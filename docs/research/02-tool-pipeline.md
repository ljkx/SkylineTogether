# 02 — Tool & Modification Pipeline, Entity Lifecycle (Cities: Skylines II)

Project: **Skyline Together** (clean-room co-op mod). Scope: how the vanilla game turns player input into persistent
entities, how derived data is regenerated, when lifecycle tags are cleared and entities destroyed, and what this means
for host-authoritative replication.

Conventions
- Paths are relative to `<audit>\decomp` unless prefixed `thirdparty/`
  (= `...\mod_audit\thirdparty`). `file.cs:N` = line N in that file.
- **[V]** = verified by reading the decompiled code. **[I]** = inference / design reasoning, not directly proven.

---

## 0. TL;DR

1. One Unity frame = `MainLoop` (in `Update`) → UI → `Cleanup` (still in `Update`) → `LateUpdate` (which runs the
   **simulation**) → `DebugGizmos`. The **tool pipeline and the whole Modification pipeline run inside MainLoop**, the
   simulation runs later in LateUpdate and feeds its structural changes back through `EndFrameBarrier`, which is
   played back at the **start of the next MainLoop**. [V]
2. Tools never touch persistent entities directly. They emit **definition entities** (`CreationDefinition` +
   `ObjectDefinition`/`NetCourse`/…, tagged `Updated`) → `Generate*Systems` (Modification1) turn them into **`Temp`
   preview entities** → on "apply", `Apply*Systems` (ApplyTool phase, inside ToolUpdate) **promote** Temps into
   permanent entities (Create: the Temp entity itself becomes permanent; Update: data copied onto `Temp.m_Original`,
   Temp deleted; Delete: original tagged `Deleted`). [V]
3. Lifecycle tags (`Created`, `Updated`, `Applied`, `BatchesUpdated`, `EffectsUpdated`, `PathfindUpdated`) are
   snapshotted by `PrepareCleanUpSystem` at the very end of MainLoop and removed by `CleanUpSystem` in the `Cleanup`
   phase of the **same frame**; entities with `Deleted` (or `Event`) are **destroyed** at the same point. [V]
4. Derived data (net geometry, compositions, lanes, sub-objects, zone blocks, aggregates, secondary lanes/objects,
   flow graphs, search trees, culling/batches, pathfinding graph) is regenerated by Modification-phase systems that
   react to `Updated`/`Deleted` (sometimes `Created`) on the **owner**. Sub-nets and sub-areas of buildings, zone cell
   contents, and some other things are **not** regenerated — only definition producers create them. [V]
5. **(a) Direct state replication works** if writes happen **before `ToolSystem` runs in MainLoop** (hard limit:
   before `PostTool` for deletions, before `Modification1` for everything), use the prefab archetypes, carry all
   non-derived source components (incl. `PseudoRandomSeed`, `BuildOrder`), tag the full topological closure
   (edge → its nodes → their connected edges, aggregates), and replicate non-regenerated children as first-class
   entities while letting regenerated children be rebuilt locally. [V mechanics / I design]
6. **(b) Definition replay is feasible but fragile on a machine whose local player is also using a tool**: Temps live in
   one global namespace — the local tool's `ApplyMode` decides whether *all* Temps are cleared, applied or kept;
   validation errors from foreign Temps block local apply; `ToolApplySystem` charges money for all Temps; results depend
   on exact world/terrain state at replay time; created entities get machine-local identities. `CreationFlags.Permanent`
   bypasses Temp/Apply but only supports pure creation. [V mechanics / I conclusions]
7. Recommended: **(a) as the authoritative convergence mechanism**; the acting player runs the vanilla tool locally
   (prediction), the resulting change-set of persistent source data is validated by the host and re-broadcast; (b) only
   for narrow cases (Permanent creations, host-side execution while the host player is idle). [I]

## 1. Frame structure and `SystemUpdatePhase`

### 1.1 The phase enum [V]
`Game/Game/SystemUpdatePhase.cs:3-38` defines: `Invalid=-1, MainLoop, LateUpdate, Modification1, Modification2,
Modification2B, Modification3, Modification4, Modification4B, Modification5, ModificationEnd, PreSimulation,
PostSimulation, GameSimulation, EditorSimulation, Rendering, PreTool, PostTool, ToolUpdate, ClearTool, ApplyTool,
Serialize, Deserialize, UIUpdate, UITooltip, PrefabUpdate, DebugGizmos, LoadSimulation, PreCulling, CompleteRendering,
Raycast, PrefabReferences, Cleanup`.

**The enum order is NOT the execution order.** A phase only runs when some code calls
`UpdateSystem.Update(phase)`. Phases are nested: a system registered in one phase calls `Update` for a sub-phase.

### 1.2 How `UpdateSystem` orders systems [V]
`Game/Game/UpdateSystem.cs`
- Registration: `UpdateAt<T>(phase)` uses `++m_AddIndex`; `UpdateBefore<T>(phase)` uses `addIndex - 1_000_000`;
  `UpdateAfter<T>(phase)` uses `addIndex + 1_000_000` (`:158-171`). The two-type overloads
  `UpdateBefore<T,Other>/UpdateAfter<T,Other>` attach T relative to a specific system via `m_RefMap` (`:173-181`,
  `:278-292`, `AddSystemUpdate :382-455`).
- Sort key: phase, then addIndex (`SystemData.CompareTo :39-47`). So inside a phase: all `UpdateBefore` entries
  (registration order) → all `UpdateAt` entries (registration order) → all `UpdateAfter` entries.
- Mods register after vanilla: `GameManager.CreateSystems()` calls `SystemOrder.Initialize` (`Game/Game.SceneFlow/GameManager.cs:621`,
  `:2392-2398`), `m_ModManager.Initialize(m_UpdateSystem)` happens later (`:678`). Consequence [V+I]: a mod's
  `UpdateBefore<X>(P)` runs after vanilla `UpdateBefore` entries of P but before all vanilla `UpdateAt` entries; a mod's
  `UpdateAfter<X>(P)` runs after vanilla `UpdateAfter` entries (e.g. after `PrepareCleanUpSystem` in MainLoop).
- Intervals: `GameSystemBase.GetUpdateInterval/GetUpdateOffset` (`Game/Game/GameSystemBase.cs:131-139`), must be a power
  of two (`UpdateSystem.cs:294-307`). Only the 3-argument `Update(phase, updateIndex, iterationIndex)` honours intervals
  (`:223-269`, check at `:241`); that overload is used only for `GameSimulation`, `EditorSimulation`, `LoadSimulation`.
  `Refresh()` distributes offsets of same-interval systems (`:309-380`).
- Exceptions in a system are caught and logged per system; the phase continues (`:201-214`).

### 1.4 Menu vs game vs editor [V]
- `GameManager.shouldUpdateWorld => m_State >= State.WorldReady` (`GameManager.cs:296`). Once the world exists, MainLoop,
  Cleanup and LateUpdate run every frame regardless of mode, including the main menu. Most systems are idle there
  because their `RequireForUpdate` queries are empty.
- Simulation choice is driven by `ToolSystem.actionMode` (`ToolSystem.cs:145`, set in `OnGamePreload :180-183` from the
  load mode): `IsEditor()` → `EditorSimulation`, `IsGame()` → `GameSimulation` (`SimulationSystem.cs:280-287`). In the
  main menu (`GameMode.MainMenu`, `Game/Game/GameMode.cs:6-15`) neither flag is set, so no simulation phase runs; the tool
  input barrier is blocked when not in game or editor (`ToolSystem.cs:253`).
- The editor uses the same tool and modification pipeline. Several systems branch on `m_EditorMode`, for example
  `ApplyObjectsSystem` (`SaveInstance`, `:597-600`).

### 1.5 Consequences of this structure for replication [V mechanics / I consequences]
- Modification runs **once per rendered frame** while the simulation runs **0–8 ticks per frame**
  (`SimulationSystem.cs:255-257`). Simulation systems write structural changes into `EndFrameBarrier`
  (example: `ZoneSpawnSystem.cs:1185,1200`), which plays back at the start of the next MainLoop
  (`SystemOrder.cs:49`). So all simulation ticks in a frame see the world as it was **before** each other's structural
  changes. The tick boundaries at which changes become visible therefore depend on frame rate. [I] Lock-step
  determinism across machines with different frame rates is not achievable without changing this. This supports the
  host-authoritative model.
- `SafeCommandBufferSystem` forbids `CreateCommandBuffer()` after playback until its `AllowBarrier<T>` runs
  (`Game/Game/SafeCommandBufferSystem.cs:16-30`, `Game/Game/AllowBarrier.cs:17-20`). Allowed windows:
  - `EndFrameBarrier`: from `AllowBarrier<EndFrameBarrier>` (MainLoop, after `ModificationSystem`, `SystemOrder.cs:62`)
    until playback at the start of the next MainLoop.
  - `ModificationBarrierN`: inside phase N only (`SystemOrder.cs:78-93`).
  - `ToolOutputBarrier`: inside ToolUpdate (`:694-696`).
  - `ToolReadyBarrier`: inside PostTool (`:697-698`).

## 2. Tool framework

### 2.1 `ToolSystem` [V] — `Game/Game.Tools/ToolSystem.cs`
- `activeTool` setter (`:84-99`) calls `RequireFullUpdate()` and fires `EventToolChanged`. `ActivatePrefabTool` (`:263-278`)
  asks each tool `TrySetPrefab`.
- `applyMode => m_LastTool?.applyMode ?? ApplyMode.None` (`:147-157`). This is **one global value, owned by the single
  active tool**.
- `ToolUpdate()` (`:308-375`): when the active tool changes, the old tool is disabled and updated once more (`:312-320`),
  the new one is enabled (`:323-326`), then `Update(ToolUpdate)` (`:327`).
- `OnUpdate()` (`:250-261`): `PreTool` → `ToolUpdate()` → `PostTool`.
- `PreDeserialize` resets to the default tool (`:610-614`).

### 2.2 `ToolBaseSystem` [V] — `Game/Game.Tools/ToolBaseSystem.cs`
- Abstract base for every tool: `toolID`, `GetPrefab`, `TrySetPrefab` (`:142,:426-428`). In `OnCreate` each tool starts
  disabled and registers itself in `ToolSystem.tools` (`:290-314`).
- `applyMode { get; protected set; }` (`:182`). Each tool sets it every update.
- `OnUpdate` is sealed and forwards to `OnUpdate(JobHandle)` (`:412-424`).
- `GetDefinitionQuery()` = `CreationDefinition` **and not** `Updated` (`:689-692`). `DestroyDefinitions(query,
  ToolOutputBarrier, deps)` destroys every matching entity through the barrier (`:506-519`, job `:31-50`). It is not
  limited to definitions this tool created: **any** `CreationDefinition` entity without `Updated`, whoever created it,
  is destroyed the next time the active tool rebuilds its definitions.
- `GetAllowApply()` (`:533-540`) returns false if any `Error` entity exists (unless `ignoreErrors`) or if
  `OriginalDeletedSystem` reported that a Temp's original was destroyed.
- `GetRaycastResult(..., out bool forceUpdate)` (`:555-559`) sets `forceUpdate` when a Temp original became `Deleted`.
  The tool then rebuilds its preview.

### 2.3 `ApplyMode` and the output phases [V]
- `ApplyMode { None, Apply, Clear }` (`Game/Game.Tools/ApplyMode.cs`).
- `ToolOutputSystem.OnUpdate` (`Game/Game.Tools/ToolOutputSystem.cs:19-31`): `Clear` → `Update(ClearTool)`;
  `Apply` → `Update(ApplyTool)`; `None` → nothing, so Temps persist unchanged.
- `ClearTool` phase = `ToolClearSystem` only (`SystemOrder.cs:712`). It tags **every** `Temp` entity `Deleted`
  (query `Temp`, `Game/Game.Tools/ToolClearSystem.cs:218`). Exception: Temp lanes and sub-objects whose Temp owner
  survives, unless `TempFlags.Essential` is set. It removes `Hidden` and adds `BatchesUpdated` on the originals
  (`ClearEntitiesJob :23-116`).
- `ApplyTool` phase order (`SystemOrder.cs:713-721`): `ToolApplySystem`, `ApplyZonesSystem`, `ApplyObjectsSystem`,
  `ApplyNetSystem`, `ApplyNotificationsSystem`, `ApplyAreasSystem`, `ApplyBrushesSystem`, `ApplyRoutesSystem`,
  `ApplyWaterSourcesSystem`. All of them write to `ToolOutputBarrier`, so they all see the same pre-apply snapshot,
  and the result is played back immediately after `ToolOutputSystem` in the same ToolUpdate.
- Typical tool behaviour (ObjectToolSystem): moving the mouse → `applyMode = Clear`, then `UpdateDefinitions` (destroy
  old definitions and create new ones). Nothing changed → `None`. Click with `GetAllowApply()` true → `Apply`, then
  immediately new definitions for the next preview (`Game/Game.Tools/ObjectToolSystem.cs:3893-3990, 4051-4180,
  4333-4345`).

### 2.4 Timeline of one placement [V]
```
Frame N-1  ToolUpdate: tool → DestroyDefinitions + new CreationDefinition(+ObjectDefinition, +Updated) via ToolOutputBarrier
           PostTool:   CourseSplitSystem splits NetCourse definitions against existing nets (ToolReadyBarrier)
           Mod1:       Generate*Systems: definitions(Updated) → Temp entities (Temp.m_Original = edited entity or Null),
                       originals get Hidden + BatchesUpdated; derived systems build Temp sub-objects/lanes/geometry…
           ModEnd:     ValidationSystem puts Error/Warning on bad Temps → blocks GetAllowApply
           Cleanup:    Updated removed from definitions and Temps (definitions survive, Temps survive)
Frame N    ToolUpdate: user clicks → tool sets applyMode=Apply (+ new preview definitions)
           ApplyTool:  ToolApplySystem charges Σ Temp.m_Cost; Apply*Systems promote Temps (see §4)
           Mod1..End:  derived systems react to Created/Updated/Deleted of the new/changed permanent entities
           Cleanup:    tags removed; Deleted (consumed Temps, deleted originals) destroyed
```

## 3. Definitions and `Temp`

### 3.1 Definition components [V]
- `CreationDefinition { m_Prefab, m_SubPrefab, m_Original, m_Owner, m_Attached, CreationFlags m_Flags, int m_RandomSeed }`
  (`Game/Game.Tools/CreationDefinition.cs`).
- `CreationFlags` (`CreationFlags.cs`): `Permanent, Select, Delete, Attach, Upgrade, Relocate, Invert, Align, Hidden,
  Parent, Dragging, Recreate, Optional, Lowered, Native, Construction, SubElevation, Duplicate, Repair, Stamping`.
- `ObjectDefinition { m_Position, m_LocalPosition, m_Scale, m_Rotation, m_LocalRotation, m_Elevation, m_Intensity, m_Age,
  m_IsDecoration, m_ParentMesh, m_GroupIndex, m_Probability, m_PrefabSubIndex }` (`ObjectDefinition.cs`).
- `NetCourse { CoursePos m_StartPosition, m_EndPosition; Bezier4x3 m_Curve; float2 m_Elevation; m_Length; m_FixedIndex }`
  (`NetCourse.cs`). `CoursePos { m_Entity, m_Position, m_Rotation, m_Elevation, m_CourseDelta, m_SplitPosition,
  CoursePosFlags m_Flags, m_ParentMesh }` (`CoursePos.cs`). `CoursePosFlags`: `IsFirst, IsLast, …, DontCreate`.
- `OwnerDefinition { m_Prefab, m_Position, m_Rotation }` (`OwnerDefinition.cs`) links child definitions (for example a
  building's sub-nets) to an owner that does not exist yet.
- Other definition payloads, selected by query: `Zoning` (zones), `Game.Areas.Node` buffer (areas), `WaypointDefinition`
  (routes), `BrushDefinition`, `WaterSourceDefinition`, `IconDefinition`, `AggregateElement`. Edges also read
  `Upgraded`, `LocalCurveCache`, `SubReplacement`, and the custom-colour components.
- Every tool creates definitions **with `Updated`**, for example `ObjectToolBaseSystem.cs:170`,
  `NetToolSystem.cs:2860-2901`, `BulldozeToolSystem.cs:751`, `ZoneToolSystem.cs:229`, `AreaToolSystem.cs:1338`.

### 3.2 `Generate*Systems` (all Modification1, `SystemOrder.cs:95-103`; edges and routes in Modification2, `:111-112`) [V]
Each one requires `CreationDefinition + Updated` plus its payload:
| System | Query (file:line) |
|---|---|
| GenerateObjectsSystem | CD+Updated, any ObjectDefinition/NetCourse (`GenerateObjectsSystem.cs:1730-1742`) |
| GenerateNodesSystem | CD+Updated, any NetCourse/ObjectDefinition (`GenerateNodesSystem.cs:2030-2042`) |
| GenerateEdgesSystem (Mod2) | CD+NetCourse+Updated **or** Updated Node/Edge without Deleted; plus Created permanent edges for BuildOrder (`GenerateEdgesSystem.cs:2185-2205`) |
| GenerateZonesSystem | CD+Zoning+Updated (`:569`) |
| GenerateAreasSystem | CD+Areas.Node+Updated (`:532`) |
| GenerateAggregatesSystem | CD+AggregateElement+Updated (`:174`) |
| GenerateBrushes / WaterSources / Notifications / Routes / Waypoints | analogous (`:158`, `:122`, `:149`, `:211`, `:615`) |

Key behaviours, using `GenerateObjectsSystem.CreateObject` (`:968-1430`) as the example:
- If `m_Original != Null`, the original gets `Hidden` and `BatchesUpdated` (`:974-978`). This is how the preview hides
  the object being edited.
- A `Temp { m_Original, m_Flags }` is built (`:989-1100`): `Delete` → `TempFlags.Delete` (+ refund cost); `Select`;
  `Relocate` → `Modify` (+ relocation cost); `Upgrade`; `Duplicate`; `Repair`; `Parent`; no original → `Create`
  (+ construction cost, game mode only).
- **Reuse of Temp entities**: previously cleared Temps (`Deleted+Temp`, `m_DeletedQuery :1743`) are recycled by
  removing `Deleted` and adding `Updated` (`:1112-1115`). Entity identity of previews is therefore unstable even locally.
- `PseudoRandomSeed` is set from `CreationDefinition.m_RandomSeed` (`:1183,:1381`; edges `GenerateEdgesSystem.cs:1513,1713`;
  nodes `GenerateNodesSystem.cs:649,1449`; areas `GenerateAreasSystem.cs:352`).
- **`CreationFlags.Permanent`**: `Temp` is added only when the flag is absent (`:1290-1292`; same in the reuse path
  `:1140`). With `Permanent` the generated entity is a normal persistent entity straight away; no Apply step is needed.
- Non-deterministic randomness: the job's `m_RandomSeed = RandomSeed.Next()` (`:1841`), and `RandomSeed` is seeded from
  `DateTime.Now.Ticks` (`Game/Game.Common/RandomSeed.cs`). One use: `UnderConstruction.m_Speed = random.NextInt(39,89)`
  for `CreationFlags.Construction` (`:1418-1422`).

### 3.3 `Temp`, `TempFlags`, `Hidden` [V]
- `Temp { m_Original, m_CurvePosition, m_Value, m_Cost, TempFlags m_Flags }` (`Temp.cs`).
- `TempFlags`: `Create, Delete, IsLast, Essential, Dragging, Select, Modify, Regenerate, Replace, Upgrade, Hidden, Parent,
  Combine, RemoveCost, Optional, Cancel, SubDetail, Duplicate` (`TempFlags.cs`).
- `Hidden` is an empty tag (`Hidden.cs`) put on originals while a Temp replaces them visually.
- All search trees and most derived systems exclude `Temp` (examples: `Game.Net/SearchSystem.cs:686-731`,
  `Game.Objects/SearchSystem.cs:344-358`, `Game.Zones/BlockSystem.cs:1136`). Previews are never part of persistent indexes.

### 3.4 Permanent definitions used by the simulation [V]
`ZoneSpawnSystem.Spawn` builds `CreationDefinition{Permanent|Construction}` + `ObjectDefinition` (`ZoneSpawnSystem.cs:614-660`),
using an archetype that contains **`Updated` and `Deleted`** (`:1090`) and is written through `EndFrameBarrier`
(`:1185`). Because the definition carries `Deleted`, it is destroyed in the same frame's Cleanup, so it is a one-shot.
Other producers: `AreaSpawnSystem.cs:453,524,575,777`, `BuildingConstructionSystem.cs:378,445`,
`ReplacePrefabSystem.cs:372,489`, `PlaceholderSystem.cs:117`, `UpgradeDeletedSystem.cs:250,348`.
Some producers (for example `BuildingConstructionSystem` sub-nets) omit `Deleted`. Those definitions are removed only
when some tool later calls `DestroyDefinitions` (§2.2). [V that no other code path destroys them; the only queries on
`CreationDefinition` are the Generate systems, CourseSplit, GuideLines, NetCourseTooltip, ClearSystem and ToolBaseSystem.]

**Permanent supports creation only** [V for objects, I for the general case]: with `m_Original != Null` the original
still gets `Hidden` (`GenerateObjectsSystem.cs:974-977`), but no Temp exists, so no Apply step ever deletes or updates the
original. The result would be a hidden original plus a duplicate. Edges and nodes have special Permanent branches that
connect to existing nodes (`GenerateNodesSystem.cs:1023-1027`, `GenerateEdgesSystem.cs:1310`), but splitting, replacing,
upgrading and deleting all rely on the Temp + Apply semantics.

## 4. `Apply*Systems` (ApplyTool phase)

### 4.1 `ToolApplySystem` [V] — `Game/Game.Tools/ToolApplySystem.cs`
Query: any of `Temp`, `Warning`, `Override` (`:118-126`). Warnings get `Deleted`, Overrides get `Updated + Overridden`,
and **Σ `Temp.m_Cost` (excluding Cancel) is subtracted directly from `PlayerMoney` on the city entity** inside the job
(`:42-74`). It charges for *every* Temp in the world, not only the ones the active tool created.

### 4.2 `ApplyObjectsSystem` [V] — `Game/Game.Tools/ApplyObjectsSystem.cs`
Query `Temp + Object` (`:922`). `HandleTempEntitiesJob.Execute` (`:327-440`):
- `Cancel` → original un-hidden + `BatchesUpdated`, Temp `Deleted` (`:474-482`).
- `Delete` → original `Deleted`; non-hidden sub-nets of the original lose `Owner` and get `Updated`; Temp `Deleted`
  (`:484-504`).
- Original exists (update/move/upgrade): copies `Attached`, and with `Upgrade` also `PrefabRef`, `Destroyed`, `Damaged`,
  `MeshColor`. It always copies `Elevation` and `LocalTransformCache` and syncs the presence of the `SubNets/SubAreas/
  SubLanes/SubObjects` buffers; removed sub-lane and sub-object buffers mark their children `Deleted` (`:354-413`).
  `Update(... Transform)` writes `Transform`, marks moving vehicles and creatures' current lanes Obsolete, and emits a
  `PathTargetMoved` event for buildings and stops (`:608-663`). Then `Recent` (cost/refund bookkeeping), **original +=
  `Updated`**, Temp `Deleted` (`:561-601`).
- No original (create): **the Temp entity itself becomes the permanent entity**. `Temp/Animation/BackSide` are removed,
  `Recent` is added if it has a cost, and `Applied + Created + Updated` are added (`Create :670-687`,
  `m_AppliedTypes :924`). A `TriggerAction(ObjectCreated)` is queued (`:433-438`).
- `PatchTempReferencesJob` (`:31-168`) re-points `Owner` and `Attached` and the `SubObject`/`OwnedVehicle`/`OwnedCreature`
  buffers from Temp owners to their originals.

### 4.3 `ApplyNetSystem` [V] — `Game/Game.Tools/ApplyNetSystem.cs`
Query `Temp` + any of `Node/Edge/Lane/Aggregate` (`:889-900`).
- Nodes (`:376-414`): `Delete`; `Replace` → original `Deleted` + Temp promoted (**new entity identity**); update → copies
  `Node`, `Owner`, `PrefabRef`, `Upgraded`, `LocalConnect`, `TrafficLights`, `Orphan`, `EditorContainer`, `Native`,
  `Standalone`, and for enabled prefabs `LandValue`, tracks, `Road`, `Pollution`, `Marker`; otherwise create.
- Edges (`:415-460`): `Replace|Combine` → **original `Deleted`, Temp becomes a new edge**. This is what happens when
  roads are split or merged. Update → copies `Owner`, `PrefabRef`, `Elevation`, `Upgraded`, `SubReplacement`, `Curve`,
  `Edge`, custom colour, `EditorContainer`, `Native`, `Road`, `Pollution`, `TramTrack`, `LandValue`.
- Lanes (`:461-540`) and other entities (`:541-552`).
- `Update` → `Applied + Updated` on the original, Temp `Deleted` (`:650-690`). `Create` → remove `Temp`, add
  `Applied + Created + Updated` (`:692-704`). `m_ApplyDeletedTypes = Applied + Deleted` (`:903`).

### 4.4 Zones / Areas / Routes / others [V]
Same pattern: `ApplyZonesSystem` copies `Cell` buffers onto original blocks (`:85-150`, query `Temp+Block :195`);
`ApplyAreasSystem` (`:158-210`, `:271-272`); `ApplyRoutesSystem` (`:274-500`, `:609-620`); `ApplyBrushesSystem` tags
`Applied + Deleted` (`:239-240`); `ApplyWaterSourcesSystem` (`:68-160`); `ApplyNotificationsSystem` (`:324-325`).

### 4.5 Implications [V+I]
- The permanent entity produced by a "create" is the machine-local Temp entity. Its `Entity` index and version are
  arbitrary and differ between machines. Splits and replacements delete originals and create new ones.
  **A stable network identity layer is mandatory** for any replication approach.
- Money, `Recent`, and triggers (achievements, tutorials, chirps) are side effects of Apply.

## 5. Lifecycle tags and destruction

### 5.1 Tag components [V] (`Game/Game.Common/*.cs`)
`Created`, `Updated`, `Deleted`, `Applied`, `BatchesUpdated`, `EffectsUpdated`, `PathfindUpdated`, and `Event` are all
empty (`Size = 1`) `IComponentData`. `Destroyed` is **not** a lifecycle tag. It is disaster or collapse state
(`m_Event`, `m_Cleared`, serialized; `Destroyed.cs`).

### 5.2 When tags are cleared and entities destroyed [V]
- `PrepareCleanUpSystem` (MainLoop, `UpdateAfter`, so last among vanilla, `SystemOrder.cs:50`) takes async snapshots of:
  `Deleted ∪ Event` (`Game/Game.Common/PrepareCleanUpSystem.cs:21-28`) and `{Created, Updated, Applied, EffectsUpdated,
  BatchesUpdated, PathfindUpdated}` without `Deleted` (`:29-41`, `:45-54`).
- `CleanUpSystem` (Cleanup phase, same frame, after `UpdateUI`) runs `EntityManager.DestroyEntity(deleted)` and
  `RemoveComponent(updated, those 6 tags)` (`Game/Game.Common/CleanUpSystem.cs:24-32`, `:48-56`).
- So **an entity tagged `Deleted` anywhere in MainLoop before `PrepareCleanUpSystem` is destroyed in the same frame**.
  Entities tagged during UI, Cleanup or LateUpdate (simulation via EndFrameBarrier, or direct EntityManager writes in
  LateUpdate) survive into the next frame's MainLoop, are processed there, and are destroyed in that frame's Cleanup.
- Tags added **after Modification but before PrepareCleanUp** (for example in `UIUpdate` or `Rendering`) are removed
  without any Modification system ever seeing them. Only PreCulling/rendering might react. This is a common bug
  source. [V from ordering; I as a warning]
- Tags are never cleared on entities that are destroyed (the updated query excludes `Deleted`), which is harmless.

## 7. Topological closure required for net changes [V + third-party evidence]
- No vanilla system propagates `Updated` from an edge to its nodes or neighbouring edges in the general case. The vanilla
  tool achieves the closure by generating **Temp copies of every affected neighbour** (the Temp nodes and edges carry
  `m_Original`, and Apply puts `Updated` on all originals). Node geometry depends on all connected edges, and edge
  geometry depends on both end nodes (`Game.Net.GeometrySystem` processes only Updated entities, `:3380-3381`).
- MoveIt (third-party, operates by direct writes) tags exactly this closure: segment → `Updated + BatchesUpdated` on
  itself, both nodes, and its aggregate (`thirdparty/CS2-MoveIt/Code/MoveIt/QAccessor/QEntity/QSegment.cs:26-43`); node →
  itself, every connected edge that ends at it, the other node of those edges, and their aggregates
  (`QNode.cs:29-51`; helper `Utils.cs:23-33`). MoveIt runs its tool in `ToolUpdate` and writes via EntityManager, before
  ModificationSystem (`thirdparty/CS2-MoveIt/Code/MoveIt/Mod.cs:34-37`). This is practical evidence that direct writes
  plus correct tags work.
- `SubElementDeleteSystem` shows the vanilla deletion closure: neighbour edges and their other nodes receive `Updated`
  (`SubElementDeleteSystem.cs:92-120`).

## 8. Determinism-relevant details [V]
- `RandomSeed` is time-seeded and per machine (`RandomSeed.cs`). It is the fallback whenever an owner lacks
  `PseudoRandomSeed`, in `SubObjectSystem`, `LaneSystem` and `SecondaryObjectSystem` (`SecondaryObjectSystem.cs:1120,4293`).
- `PseudoRandomSeed { ushort m_Seed }` is serialized and gives deterministic sub-streams per purpose (`kSubObject`,
  `kSubLane`, `kSecondaryObject`, `kSplitEdge`, …) (`PseudoRandomSeed.cs`). Derived generation is deterministic **if
  `PseudoRandomSeed` is replicated** for owners.
- `BuildOrder`: Temp edges take values from the global counter. `UpdateBuildOrderJob` only raises the counter to
  `max(existing)+1` from Created permanent edges (`GenerateEdgesSystem.cs:1919-1943, 2346-2357`). Replicating the
  `BuildOrder` component keeps counters consistent. It matters for zone block ordering (`BlockSystem` uses it).
- `UpdateFrame` (shared component, decides the simulation tick slot): for Created entities `UpdateGroupSystem` chooses
  the least-loaded group (`FindUpdateIndex`) **unless the chunk has `Applied`**, in which case the current UpdateFrame
  is kept (`UpdateGroupSystem.cs:407-460`). Temps inherit the original's frame (`:343-346`).
- `UnderConstruction.m_Speed` from `RandomSeed.Next()` (`GenerateObjectsSystem.cs:1418-1422`).

## 9. CRITICAL QUESTION (a): direct state replication

> If a remote machine creates/updates/deletes the same persistent entities with identical component data directly
> and tags them `Created`/`Updated`/`Deleted`, will derived systems rebuild correctly? In which phase must this happen?

### 9.1 Answer: yes for derived data, with conditions
The game's own non-tool producers already do exactly this. Examples: `ZoneSpawnSystem` via Permanent definitions; MoveIt
via direct writes plus `Updated`; `SubElementDeleteSystem` and `BlockSystem` via `Updated`/`Deleted` tags. Every derived
system in §6 keys only on tags plus current component data. It never checks whether a change came from a tool, except
via `Applied` (§5.1). [V]

Conditions [V mechanics → I requirements]:
1. **Phase / timing**
   - *Hard limits*: deletions of owners with `SubNet/SubArea/SubRoute/OwnedVehicle` must be visible **before PostTool**,
     because `SubElementDeleteSystem` runs only there (`SystemOrder.cs:725`). Otherwise sub-nets keep a dangling
     `Owner` after the building is destroyed. All other writes must be visible **before Modification1**.
     Writing in Modification2B or later makes earlier sub-phases miss the change. Writing after ModificationEnd and
     before `PrepareCleanUpSystem` loses the tags entirely (§5.2).
   - *Recommended*: apply remote mutations **at the start of MainLoop, before `ToolSystem`**:
     - either as a mod system registered `UpdateBefore<RemoteApplySystem>(SystemUpdatePhase.MainLoop)`, which runs after
       vanilla `EndFrameBarrier` playback and before `RaycastSystem`/`ToolSystem` (§1.2);
     - or by recording an ECB on `EndFrameBarrier` at any point between `AllowBarrier<EndFrameBarrier>` and the end of
       the frame. This is exactly how simulation changes enter the pipeline.

     Benefits:
     - (i) `OriginalDeletedSystem` (PreTool) sees remote deletions and forces the local tool to rebuild its preview and
       blocks apply (`OriginalDeletedSystem.cs:14-56, 100-125`; `ToolBaseSystem.cs:533-559`);
     - (ii) `SubElementDeleteSystem` runs;
     - (iii) everything is derived before `LateUpdate`, so the simulation never sees half-built entities
       (for example an edge without geometry or lanes).
   - Writing in LateUpdate with a direct EntityManager call also gets processed next frame, but simulation ticks in that
     same LateUpdate would see un-derived entities. [I] Avoid it.
2. **Creation**: create with the prefab archetype (`NetData.m_EdgeArchetype/m_NodeArchetype`, `ObjectData.m_Archetype`,
   `MovingObjectData.m_StoppedArchetype`, `AreaData.m_Archetype`; see `GenerateEdgesSystem.cs:697`,
   `GenerateNodesSystem.cs:1407`, `GenerateObjectsSystem.cs:1224-1241`, `GenerateAreasSystem.cs:259`). Those archetypes
   already include `Created + Updated`. Set every **source** component: `PrefabRef`, `Transform`/`Node`/`Edge`/`Curve`,
   `Elevation`, `Owner`, `Attached`, `Upgraded`, `PseudoRandomSeed`, `BuildOrder`, `Road`, `LocalConnect`,
   `TrafficLights`, `Native`, colour, and so on. The Apply copy lists in §4.2/§4.3 are a good catalogue of
   "user-authored" components. Never replicate `Temp`/`Hidden`.
3. **Updates**: write the changed source components and add `Updated` on the full closure (§7), plus `BatchesUpdated` for
   visual refresh (as MoveIt does). For player-originated changes also add `Applied`. That reproduces the vanilla Apply
   signature: `UpdateFrame` is kept, route paths are rechecked, PreCulling applied-flags are set.
4. **Deletes**: add `Deleted` to the entity **and** explicitly to anything the tool would have deleted (orphan nodes are
   decided by the tool, not by a system). Add `Updated` to the surviving neighbours (closure). Regenerated children
   (sub-objects, sub-lanes, blocks, secondary objects) are deleted locally by their systems; sub-nets and sub-areas are
   handled by `SubElementDeleteSystem` if the write happens before PostTool.
5. **Children: replicate vs regenerate**
   - Regenerated locally (do **not** replicate creation; match them by stable key if simulation state must be attached):
     sub-objects, sub-lanes, secondary lanes/objects, zone blocks, aggregates, net/area geometry, compositions,
     electricity/water flow graph entities, pathfinding graph, search trees, batches.
   - First-class (must replicate): edges and nodes including building sub-nets, sub-areas, buildings/props/trees
     (top-level objects), routes and waypoints, zone `Cell` data (on blocks that each machine generates itself → key by
     owner edge + `Block` geometry [I]), custom names attached to regenerated aggregates [I].
6. **Identity**: entity indices differ per machine (§4.5). All entity references inside replicated components (`Owner`,
   `Edge.m_Start/m_End`, `Attached.m_Parent`, `PrefabRef.m_Prefab` → map via prefab ID, …) must be remapped through a
   network-ID table.
7. **Side effects of `Created` on remote machines** run locally: XP (`XPBuiltSystem.cs:184`, `NetXPSystem.cs:268-269`),
   milestones, `Game.Net.InitializeSystem`, building initializers, achievements and triggers. On clients these must be
   suppressed or overwritten by authoritative values (money, XP, milestones are host-owned). [I]
8. **Job safety**: a main-thread `EntityManager` structural change completes all running jobs (sync point). An ECB on a
   proper barrier avoids extra stalls. [I, standard Unity.Entities behaviour]

### 9.2 What can break (a)
- Missing closure tags lead to stale node geometry, wrong intersections, stale lanes. [V, §7]
- Writing in the wrong phase leads to missed `SubElementDeleteSystem` (dangling sub-nets) or tags cleared unseen. [V, §5.2, §6]
- Replicating regenerated children *and* letting them regenerate produces duplicates. [I]
- Missing `PseudoRandomSeed` produces different sub-object, lane and secondary-object variations. [V, §8]
- New zone blocks start empty. Zoning carried by blocks must be replicated after the remote `BlockSystem` has (re)built
  them. [V for empty init; I for the strategy]
- Simulation state that references derived children (vehicles on lanes, parked cars, …) needs key-based translation. [I]

## 10. CRITICAL QUESTION (b): replaying tool actions via definitions

> Could we inject the same `CreationDefinition` entities on the remote and let the game's Apply systems do the work?

### 10.1 What the replay needs [V mechanics]
1. Definition entities with **`Updated`**, created early enough:
   - via `ToolOutputBarrier` inside ToolUpdate, or any time before PostTool, so that `CourseSplitSystem` (PostTool,
     query `CreationDefinition+NetCourse+Updated`, `CourseSplitSystem.cs:4081`) processes net courses;
   - at the latest before Modification1 for non-net definitions. Third-party precedent: TreeController edits definitions
     in a system registered `UpdateBefore<...>(Modification1)` (`thirdparty/Tree_Controller/Tree_Controller/TreeControllerMod.cs:119`,
     `Systems/TreeObjectDefinitionSystem.cs:69-150`).
2. The full definition set the tool produced: main definition, every neighbour/affected-entity definition (Delete,
   Upgrade, Parent flags), sub-net `NetCourse`s and sub-area definitions with `OwnerDefinition`, auxiliary components
   (`Upgraded`, `LocalCurveCache`, `SubReplacement`, colour, `EditorContainer`), and the `m_RandomSeed` values.
   Entity references remapped (world entities via network IDs, prefabs via prefab IDs).
3. After Generate (frame N), an **ApplyTool phase**. That only happens when the local active tool's `applyMode == Apply`
   (`ToolOutputSystem.cs:22-30`).

### 10.2 Why it is fragile [V facts → I conclusions]
- **Shared Temp namespace**:
  - `ToolClearSystem` deletes *all* Temps whenever the local tool reports `Clear` (`ToolClearSystem.cs:218`). This
    happens on almost every mouse move.
  - Every Apply system applies *all* Temps (queries `Temp+Object`, `Temp+Node/Edge/Lane/Aggregate`, …) when the local
    tool reports `Apply`. A remote player's replayed preview would be erased by the local preview, or committed by the
    local player's click.
  - `GenerateObjectsSystem` also recycles any `Deleted+Temp` (`:1743`, `:1112-1115`).
- **Validation and blocking**: `ValidationSystem` validates all `Temp+Updated` (`ValidationSystem.cs:1917-1919`) and
  creates `Error`s. `ToolBaseSystem.GetAllowApply` blocks on *any* `Error` (`:533-540`), so remote Temps can block the
  local player's placement.
- **Money**: `ToolApplySystem` subtracts the cost of *all* Temps from `PlayerMoney` (`:42-74`). Replays would charge
  again on every machine. Money must be host-authoritative anyway.
- **Definition cleanup**: the local active tool destroys *every* definition lacking `Updated` (`ToolBaseSystem.cs:506-519,
  689-692`). Harmless for one-shots, but it means definitions cannot be kept alive across frames.
- **State sensitivity**: Generate, CourseSplit and validation results depend on the exact current world (search trees,
  existing nets, terrain height, water surface: `CourseSplitSystem.cs:4085-4186`; `GenerateEdgesSystem` uses
  `TerrainSystem`/`WaterSystem`). Any divergence at replay time (latency, interleaved host actions, unsynced terraforming)
  gives a different result, so authoritative correction is needed anyway.
- **Identity**: results are machine-local Temp entities promoted to permanent (§4.2/4.3), so a post-hoc matching step is
  still required.
- **Randomness**: `m_RandomSeed` makes `PseudoRandomSeed` deterministic, but `RandomSeed.Next()` paths remain
  (`UnderConstruction.m_Speed`; children whose owners lack `PseudoRandomSeed`).
- **Workarounds** (all [I]):
  - Make a custom `ToolBaseSystem` "ReplayTool" the active tool for the replay frames. This kills the local player's
    tool state: switching disables the old tool (`ToolSystem.cs:312-320`) and `OnStopRunning` resets actions and
    infoview (`ToolBaseSystem.cs:330-337`).
  - Call `UpdateSystem.Update(ApplyTool)` manually. That still applies the local player's Temps.
  - Both damage UX and the "perfectly synced" goal.
- **`CreationFlags.Permanent` variant**: no Temp, no Apply, no cost, no interference with local Temps (Generate creates
  permanent entities directly; the ZoneSpawn pattern of definition + `Updated` + `Deleted`). But it only supports
  creation: no edits, deletes, upgrades or splits (§3.4). It also skips Apply-only bookkeeping (`Applied`, `Recent`,
  triggers).

### 10.3 Faithfulness comparison
| Aspect | (a) direct state | (b) definition replay |
|---|---|---|
| Uses vanilla derived regeneration | yes | yes |
| Uses vanilla Generate/Apply semantics (splits, upgrades, refunds) | no — the originator's machine runs them; others receive the result | yes, but result depends on remote world state |
| Converges to host truth | yes, by construction (host data is copied) | only if every machine's state was identical at replay time |
| Interferes with the local player's tool | no (only via `OriginalDeleted`, which is designed for this) | yes (shared Temps, errors, ApplyMode, money) |
| Needs identity mapping | yes | yes (post-hoc) |
| Needs knowledge of the component catalogue | yes (source components + closure + which children regenerate) | yes (definition catalogue per tool) |
| Handles simulation-originated changes (zone growth, collapse, upgrades) | same mechanism | not applicable (they are not tool actions) |

### 10.4 Recommendation [I]
- **Primary: (a)**. The host applies validated changes, extracts the persistent **source** components of everything an
  action created, changed or deleted (one frame after its own Apply and Modification, so derived data and identities are
  final), and broadcasts a change-set keyed by network IDs. Every machine applies it at MainLoop start (§9.1) with
  `Created/Updated/Deleted (+Applied, +BatchesUpdated)` on the closure, and lets local Modification regenerate derived
  data. Periodic hashing of source components plus targeted re-sends, with save/load as the last resort, guarantees
  convergence.
- **Client actions**: the acting client runs the vanilla tool locally (instant feedback, exact vanilla semantics), then
  sends either its resulting change-set (host validates: cost, permissions, conflicts) or its definitions (host replays
  when its own player has no active preview). Either way the host re-broadcasts the authoritative change-set, and the
  originator reconciles (replace predicted entities with host IDs). The host's own player is unaffected under (a).
- Use (b) **only** for pure creations via `Permanent` one-shot definitions (definition + `Updated` + `Deleted`, the
  ZoneSpawn pattern) where letting each machine generate is cheaper than shipping the result. Even then, verify the
  result against the host.
