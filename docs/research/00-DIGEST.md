# Research digest

Summaries, key findings, risks and open questions of every research report. Full reports (with code citations) are the numbered files next to this one.


## 01-serialization.md

CS2 serialization lives in Colossal.Core/Colossal.Serialization.Entities. Each serializable component, buffer or shared component implements public ISerializable.Serialize<TWriter>/Deserialize<TReader>. Systems implement IDefaultSerializable or IJobSerializable. All entity remapping happens inside IWriter.Write(Entity) and IReader.Read(out Entity): the stock BinaryWriter/BinaryReader do a plain NativeArray<Entity> table lookup (writer table indexed by live Entity.Index holding the save index and a version check; reader table indexed by save index). Because IWriter/IReader, BinaryWriter/BinaryReader, the Entity*Data carriers, ComponentSerializerLibrary, ComponentSerializerChunk and the drivers are all public, we can serialize any entity, component or buffer at runtime with our own writer/reader backed by our net-ID map, and apply the result on another machine. The main internal obstacle is that reader Contexts need format tags. ContextFormat.EnableTag is internal, and Has() on a Context built with the 3-arg constructor dereferences a null pointer, so we need reflection or UnsafeUtility.As to enable all tags, plus Purpose.LoadGame and Game.Version.current. The game's EntityDeserializer cannot do partial updates: it always creates new entities, takes an exclusive transaction, and calls SetDefaults on every registered system absent from the stream. It is only usable with an empty SystemSerializerLibrary. Full snapshots work as follows. SaveGameSystem.stream/context/RunOnce are public, so the host can save to a MemoryStream. Loading needs a file path (StreamBinaryReader uses AsyncReadManager), so the client writes a temp file and builds AsyncReadDescriptor(name, path). The full load entry GameManager.Load(..., AsyncReadDescriptor, ...) is private and needs reflection. A mod NetId ISerializable component is automatically included in saves (ModManager calls TypeManager.InitializeAdditionalTypes and SerializerSystem.SetDirty, and the query includes mod types), which gives a clean join-time ID map. Prefab references must be mapped by PrefabID. Derived data (IEmptySerializable components such as EdgeGeometry and Composition, plus runtime-only components) is rebuilt after load through OnGameLoaded, RequiredComponentSystem and Updated tagging.


**Key findings**

- ISerializable (Serialize<TWriter>/Deserialize<TReader>) is public on all ~744 serializable component/buffer types; callable with any IWriter/IReader struct (Colossal.Core/Colossal.Serialization.Entities/ISerializable.cs:3-8).
- Entity remap is only in BinaryWriter.Write(Entity) (BinaryWriter.cs:128-156, writes table[e.Index].Index if version matches else -1) and BinaryReader.Read(out Entity) (BinaryReader.cs:146-157, table[i] or Entity.Null); tables are supplied via public Initialize(...), so custom tables or custom IWriter/IReader give full control.
- Writer/reader are passed by value into nested calls; BinaryReader keeps its cursor in NativeReference<int> (BinaryReader.cs:14-18,159-163) - custom readers must do the same.
- Context(Purpose,Version,Hash128) has no format storage; ContextFormat.Has indexes UnsafeList without checks (ContextFormat.cs:31-35, UnsafeList.cs:210-222) -> crash when any Deserialize calls reader.context.format.Has (46 Game files, e.g. PrefabID.cs:100). EnableTag is internal; enable all tags via reflection or UnsafeUtility.As. Writers never read format (only purpose in CityConfigurationSystem.cs:278,326).
- EntitySerializer stream layout: metadata(version, buffer format, tag names) / component type table (byte kind + AssemblyQualifiedName) / system type table / archetype table / per-archetype component blocks / per-system blocks (EntitySerializer.cs:582-701). Unknown types are skipped via ObsoleteComponentSerializer (EntityDeserializer.cs:337-374).
- EntityDeserializer always creates new entities (EntityDeserializer.cs:482-541), uses BeginExclusiveEntityTransaction (:197) and calls SetDefaults on registered systems missing from the stream (:434-442,627-631) - unsafe for partial updates unless SystemSerializerLibrary is empty.
- SerializerSystem exposes componentLibrary/systemLibrary publicly and serializes query Any{LoadedIndex, PrefabRef, ..., mod ISerializable types} minus Temp/Deleted/EffectInstance/LivePath/NetCompositionData with CompressedZStd and requireEnabled PrefabData (Game.Serialization/SerializerSystem.cs:41-43,95-110,171-210).
- SaveGameSystem.stream/context/RunOnce and LoadGameSystem.dataDescriptor/context/RunOnce are public (SaveGameSystem.cs:22-64, LoadGameSystem.cs:20-57); WriteSystem disposes the stream at the end (WriteSystem.cs:52-61,133-141); ReadSystem reads only from a file path via StreamBinaryReader/AsyncReadManager (StreamBinaryReader.cs:17-48).
- GameManager.Save is public but uses private SaveSimulationData and internal PrefabSystem.SavePrefabAssets (climate/water/terrain render prefabs into the package) (GameManager.cs:934-1012, PrefabSystem.cs:378-437); the full-featured GameManager.Load(GameMode,Purpose,AsyncReadDescriptor,Hash128,Guid) is private (GameManager.cs:1046-1144).
- Mod ISerializable components/systems are included automatically: ModManager.AfterLoadAssembly -> TypeManager.InitializeAdditionalTypes + SerializerSystem.SetDirty (ModManager.cs:146-150); ComponentSerializerLibrary scans all TypeManager types (ComponentSerializerLibrary.cs:43-99). A NetId component gives a join-time ID map.
- Prefab references: PrefabRef is a plain Entity reference; prefab entities are saved with PrefabData.m_Index renumbered (BeginPrefabSerializationSystem.cs:109-193), PrefabSystem.Serialize writes PrefabIDs (PrefabSystem.cs:826-864), ResolvePrefabsSystem + PrefabReferences.Check remap stubs to live prefabs on load (ResolvePrefabsSystem.cs:445-540, PrefabReferences.cs:61-123). Runtime sync must map prefabs by PrefabID.
- Derived data is not serialized: IEmptySerializable data components (EdgeGeometry, Composition, CullingInfo), runtime-only tags (Updated/Created/Deleted/Temp); rebuilt via OnGameLoaded (GameSystemBase.cs:25,76,119; GeometrySystem.cs:3385-3404), RequiredComponentSystem (RequiredComponentSystem.cs:753-793) and ~45 Deserialize-phase fix-up systems (SystemOrder.cs:738-898).

**Risks**

- Reader Context without enabled format tags dereferences a null pointer and crashes the game; tag enabling requires internal access (reflection or UnsafeUtility.As trick).
- System state (57+ IDefaultSerializable, 16+ IJobSerializable/CellMap systems) is serialized separately and its Deserialize methods have load-time side effects (e.g. TerrainSystem.cs:3133-3163, SimulationSystem resets timers) - not safely re-appliable at runtime; global state must be synced via commands or full resync.
- EntityDeserializer resets every system missing from the stream via SetDefaults and takes an exclusive entity transaction - catastrophic if misused for partial loads.
- No in-memory load path: snapshots must be written to a temp file; full load requires reflection on private GameManager.Load; RunOnce alone skips onGamePreload/loading-screen state.
- Bare SaveGameSystem snapshots omit package prefab assets (climate/water/terrain render) bundled only by GameManager.Save/internal SavePrefabAssets; custom map content may be missing on clients.
- Identical game version (Game.Version.current), mod set and prefab/content set are mandatory; wire formats branch on version in ~205 files and on Purpose (e.g. ServiceFee NewGame reset).
- Stock reader turns unknown/out-of-batch references into Entity.Null silently; prefab Entity values differ per machine; out-of-order arrival requires deferred reference resolution in a custom reader.
- Derived/runtime components are not serialized; runtime-applied entities need Updated/Created tagging and the same required components that RequiredComponentSystem adds after load, or the simulation/render state diverges.
- Saving mutates host state slightly (TrimPathsSystem, PrefabData enable/index renumbering) and blocks frames on large cities.
- Generic serializer jobs instantiated with mod-defined writer/reader types will not be Burst-compiled (managed fallback); Burst status of the game's own MakeGenericType-created serializer jobs is unknown.

**Open questions**

- Are the game's generic ComponentSerializer jobs (created via MakeGenericType/Activator) Burst-compiled in the shipped build?
- How long does the Serialize phase take for large cities (join/resync cost), and can it run without a visible hitch?
- What breaks when a client loads a bare sim snapshot without the save package's climate/water/terrain render prefabs from a custom map?
- Per domain (net, objects, areas, zones, routes, citizens, vehicles): which components must be sent, which need Updated/Created tags, and which RequiredComponentSystem components must be added when spawning entities from deltas?
- Does deserializing component deltas into existing values (preserving non-serialized fields) vs default-then-deserialize matter for specific components? This needs a per-type audit.
- Is calling GameManager's private Load via reflection stable across game patches, or should we create a transient SaveGameData asset and use the public Load(GameMode, Purpose, IAssetData)?

## 02-tool-pipeline.md

A Unity frame runs in this order: MainLoop (in Update), then UI, then Cleanup, then LateUpdate (where SimulationSystem runs PreSimulation, 0-8 Game/EditorSimulation ticks and PostSimulation). The tool pipeline and the entire Modification pipeline run inside MainLoop, in the order ToolSystem (PreTool → ToolUpdate with ClearTool/ApplyTool nested via ToolOutputSystem → PostTool), then ModificationSystem (Mod1..ModEnd). Simulation structural changes go through EndFrameBarrier and play back at the start of the next MainLoop (SystemOrder.cs:47-77, ToolSystem.cs:250-327, ToolOutputSystem.cs:19-31, SimulationSystem.cs:188-296). Tools emit CreationDefinition entities tagged Updated. Generate*Systems (Mod1/Mod2) turn them into Temp previews. On apply, Apply*Systems promote the Temps: a create turns the machine-local Temp entity itself into the permanent entity, an update copies data onto Temp.m_Original and adds Updated, and splits/replaces delete originals and create new entities. ToolApplySystem charges money for every Temp in the world. PrepareCleanUpSystem (last in MainLoop) snapshots Created/Updated/Applied/BatchesUpdated/EffectsUpdated/PathfindUpdated and Deleted/Event entities. CleanUpSystem then removes those tags and destroys the Deleted/Event entities in the same frame's Cleanup phase. Derived data is rebuilt purely from tags plus current data: net geometry (Mod4), lanes (Mod4), zone blocks (Mod4), sub-objects (Mod2B), aggregates (Mod2B), secondary lanes/objects (Mod4B), search trees (Mod5), pathfinding (ModEnd) and culling (PreCulling). The exceptions are prefab sub-nets/sub-areas and zone Cell contents, which only definition producers create. Approach (a), direct state replication, is sound if four conditions hold. First, writes happen before ToolSystem in MainLoop: at the latest before PostTool, because SubElementDeleteSystem runs only there, and before Modification1 for everything else. Second, entities are created from prefab archetypes. Third, all source components including PseudoRandomSeed and BuildOrder are copied. Fourth, the full net closure is tagged; MoveIt does exactly this. Approach (b), definition replay, conflicts with the local player's tool because all Temps share one namespace: the local ApplyMode clears or applies every Temp, foreign Temps' Errors block local apply, and money is charged on every machine. It also depends on identical world state at replay time. CreationFlags.Permanent avoids the Temp conflicts but supports only pure creation. Recommendation: use (a) as the authoritative convergence mechanism, with the acting client running the vanilla tool locally as prediction; use (b) only for Permanent one-shot creations.


**Key findings**

- Execution order is not enum order. GameManager.Update runs MainLoop then Cleanup; GameManager.LateUpdate runs LateUpdate (SimulationSystem) and DebugGizmos. ToolSystem→PreTool/ToolUpdate/PostTool, ToolOutputSystem→ClearTool/ApplyTool (nested inside ToolUpdate), ModificationSystem→Mod1..ModEnd, PreRenderSystem→PreCulling, RenderingSystem→Rendering (GameManager.cs:712-733,2401-2425; SystemOrder.cs:47-77,694-726).
- UpdateSystem ordering is by phase, then addIndex. UpdateBefore=-1e6, UpdateAt=+0 and UpdateAfter=+1e6, in registration order. Mods register after SystemOrder.Initialize, so a mod's UpdateBefore(MainLoop) runs after EndFrameBarrier playback and before ToolSystem (UpdateSystem.cs:39-47,158-181; GameManager.cs:621,678).
- SafeCommandBufferSystem barriers are usable only between AllowBarrier<T> and playback. EndFrameBarrier accepts commands from after ModificationSystem until the start of the next MainLoop (SafeCommandBufferSystem.cs:16-30; SystemOrder.cs:49,62).
- ToolSystem.applyMode is the single active tool's ApplyMode. Clear means ToolClearSystem deletes ALL Temp entities; Apply means every Apply* system processes ALL Temps; None leaves Temps untouched (ToolSystem.cs:147-157; ToolOutputSystem.cs:22-30; ToolClearSystem.cs:218).
- Every tool creates definitions with the Updated tag. Generate*Systems (Mod1, edges/routes Mod2) require CreationDefinition+Updated, hide originals (Hidden+BatchesUpdated), recycle Deleted Temps, and set PseudoRandomSeed from CreationDefinition.m_RandomSeed (GenerateObjectsSystem.cs:968-1430,1730-1743).
- CreationFlags.Permanent skips Temp, so the generated entity is persistent immediately; ZoneSpawnSystem uses definition+Updated+Deleted one-shots via EndFrameBarrier. It supports only creation: with m_Original set, the original is hidden and never replaced (GenerateObjectsSystem.cs:974-977,1290-1292; ZoneSpawnSystem.cs:614-660,1090,1185).
- Apply create path: the Temp entity itself becomes the permanent entity (Temp removed; Applied+Created+Updated added). Update path: data is copied to the original, the original gets Updated (+Applied), and the Temp gets Deleted. Net Replace/Combine deletes the original and creates a new entity (ApplyObjectsSystem.cs:561-687; ApplyNetSystem.cs:376-460,650-704).
- ToolApplySystem subtracts the summed Temp.m_Cost of ALL Temps directly from PlayerMoney during ApplyTool (ToolApplySystem.cs:42-74).
- PrepareCleanUpSystem (UpdateAfter MainLoop) snapshots the 6 update tags and Deleted/Event entities. CleanUpSystem (Cleanup phase, same frame) removes the tags and destroys those entities. Tags added after ModificationEnd but before PrepareCleanUp are wiped without any Modification system seeing them (PrepareCleanUpSystem.cs:21-54; CleanUpSystem.cs:24-56).
- Derived regeneration keyed on Updated/Deleted owners: SubObjectSystem (Mod2B), AggregateSystem (Mod2B), Net.ReferencesSystem (Mod2B, does NOT propagate Updated), CompositionSelect (Mod3), Net.GeometrySystem, LaneSystem and BlockSystem (Mod4), SecondaryLane/ObjectSystem (Mod4B), SearchSystems and UpdateCollect (Mod5), LanesModified (ModEnd), PreCulling (Updated or BatchesUpdated).
- SubElementDeleteSystem (deletes or detaches sub-nets, sub-areas, sub-routes and owned vehicles of Deleted owners, and updates neighbours) runs only in PostTool, writing via ToolReadyBarrier. Remote deletions must therefore be applied before ToolSystem's PostTool (SubElementDeleteSystem.cs:62-160,314-330; SystemOrder.cs:725).
- Prefab sub-nets and sub-areas are created only by definition producers (tools, ZoneSpawn, BuildingConstruction, AreaSpawn), never regenerated by Modification systems. New zone blocks start with empty Cell buffers (BlockSystem.cs:986-1001).
- Net changes require tagging the topological closure (edge, both nodes, connected edges, aggregates); the game does not propagate it. MoveIt's direct-write implementation does exactly this from ToolUpdate (thirdparty CS2-MoveIt QSegment.cs:26-43, QNode.cs:29-51).
- Determinism: RandomSeed is time-seeded and is the fallback when an owner lacks PseudoRandomSeed (SubObjectSystem.cs:1009, LaneSystem.cs:675). The Applied tag preserves the existing UpdateFrame in UpdateGroupSystem; otherwise UpdateFrame is load-balanced locally (UpdateGroupSystem.cs:407-460).
- OriginalDeletedSystem (PreTool) detects Deleted or destroyed Temp originals, forces the local tool to rebuild its preview and blocks apply. It is the game's built-in handling for the world changing under a preview, so remote deletions applied before ToolSystem are tolerated by local tools (OriginalDeletedSystem.cs:14-125; ToolBaseSystem.cs:533-559).
- ValidationSystem validates all Temp+Updated entities; GetAllowApply blocks if any Error exists. Foreign Temps from a definition replay would block the local player (ValidationSystem.cs:1917-1919; ToolBaseSystem.cs:533-540).
- Load path: LoadGameSystem runs Deserialize inside MainLoop before ModificationSystem; systems with an m_Loaded flag then recompute all entities. Save/load is a valid full-rebuild resync (LoadGameSystem.cs:51-57; Net/GeometrySystem.cs:3386-3410).

**Risks**

- Entity identity is machine-local: Apply turns local Temp entities into permanent ones, and splits/replaces create new entities. A robust network-ID layer is mandatory and must also map prefab entities by prefab ID.
- The simulation runs 0-8 ticks per rendered frame, while structural changes are deferred via EndFrameBarrier and processed once per frame. Tick-level lockstep across machines with different frame rates is impractical, so a host-authoritative model is required.
- Wrong write phase silently breaks things: Deleted applied after PostTool leaves dangling sub-nets; tags added after ModificationEnd are cleared unseen; writes during LateUpdate expose half-built entities to simulation ticks.
- Missing closure tags (neighbour nodes and edges, aggregates) cause stale geometry, intersections and lanes.
- Replicating regenerated children (sub-objects, sub-lanes, blocks, secondary objects, aggregates) while also letting them regenerate creates duplicates. Their simulation state must be matched via stable keys instead.
- Zone Cell data lives on locally regenerated block entities that start empty. It needs key-based replication after BlockSystem has run.
- Side effects of Created and Apply on clients (XP, milestones, triggers, initializers, PlayerMoney charges) diverge unless suppressed or overwritten by host values.
- Definition replay (b) conflicts with the local player's tool because all Temps share one namespace (ApplyMode, ToolClearSystem, validation errors, money). Making a ReplayTool active destroys the local tool state.
- Definition replay results depend on exact world, terrain and water state at replay time (CourseSplit, Generate). Any prior divergence compounds.
- RandomSeed.Next() fallbacks (UnderConstruction speed, owners without PseudoRandomSeed) produce non-deterministic results.
- The local active tool's DestroyDefinitions removes ANY CreationDefinition without Updated, so injected definitions cannot persist across frames.

**Open questions**

- What is the exact list of source vs derived components per entity family (nets, buildings, props, areas, routes, zones)? Cross-check with the serialized component set.
- How should zone cells be replicated when blocks are recreated (CellCheckSystem and zone-overlap migration logic)?
- How are custom names (NameSystem) handled for regenerated aggregates and other entities?
- Who should own Recent (refund window) and PlayerMoney, and how should they reconcile with client-side predicted tool costs?
- Can the host safely execute client definitions when its own player has an active preview (for example by deferring until the host's ApplyMode is None and no host Temps exist), or should clients always send post-apply change-sets?
- Terrain and water modifications (TerrainToolSystem, brushes, water sources) are not entity-centric and need a separate replication path; not covered here.
- Do the area GeometrySystem and SubAreaReferencesSystem fully rebuild remotely created areas, including LocalNodeCache in editor mode?

## 03-simulation.md

CS2's simulation is driven by SimulationSystem (registered in LateUpdate). It runs 0..8 GameSimulation ticks per rendered frame at a nominal 60 ticks/s at speed 1; UI speeds are 1/2/4. The tick count is capped by wall-clock deltaTime, measured job cost (frameDuration) and pending pathfinding deadlines. Simulation structural changes go through EndFrameBarrier, which plays back once at the start of the next rendered frame, and the Modification phases (initialization, references, UpdateGroupSystem) also run once per rendered frame. As a result, simulation results depend on how ticks were batched into frames. Work is sliced with power-of-two update intervals and offsets (auto-assigned in UpdateSystem.Refresh, which depends on the registered system and mod set) and with a 16-group UpdateFrame shared component. A day is 262144 ticks; moving objects update every 16 ticks into a 4-slot TransformFrame ring, and rendering interpolates 32 ticks behind. Randomness comes from a single global RandomSeed stream seeded from DateTime.Now. Rendering, tools and audio also draw from it, and jobs derive their streams from unfilteredChunkIndex, so per-entity determinism is lost. There are 214 parallel NativeQueue writers whose drain order is set by thread timing. Pathfinding results apply whenever worker threads finish, water is a GPU simulation with a smoothDeltaTime time step, terrain heights come from GPU readbacks, and Entity IDs differ per machine. Deterministic lockstep is therefore not feasible without rewriting about 100 Burst jobs and the frame loop. The recommended design is host-authoritative with a follower client. Clients chase the host's frameIndex (so time, climate and interpolation stay correct), disable gameplay GameSimulation and gameplay-producing ModificationEnd systems, and apply host deltas before ModificationSystem so the vanilla pipeline processes them. System-level state can be synced with the systems' own ISerializable implementations, and moving objects replicated as interest-managed TransformFrame snapshots.


**Key findings**

- SimulationSystem (Game.Simulation/SimulationSystem.cs:188-296) runs in LateUpdate. Ticks per frame = floor(timer*60), capped by pathfinding pending frame (l.231-245), CPU budget (l.246-253) and clamp(round(speed*2),1,8) (l.255-257). Only frameIndex is serialized (l.135-146).
- Per rendered frame order: EndFrameBarrier playback first (SystemOrder.cs:49, EndFrameBarrier.cs:34-43), then ToolSystem, then ModificationSystem (Modification1..5 and ModificationEnd, once per frame, ModificationSystem.cs:17-27), then PathfindResultSystem, then Rendering, then the sim ticks in LateUpdate. Command buffers from all ticks of a frame apply together at the start of the next frame.
- Update intervals: UpdateSystem.cs:241 runs a system when (frameIndex & (interval-1)) == offset. Offsets of -1 are auto-assigned in Refresh() (l.309-380), so they depend on the registered system set and host and clients need an identical mod set.
- UpdateFrame shared component (serialized) puts entities in 16 groups, assigned least-populated-first by UpdateGroupSystem (Modification5). SimulationUtils.GetUpdateFrame implements the per-day slicing. TimeSystem.kTicksPerDay = 262144 and 12 days per year (TimeSettingsPrefab.cs:10).
- Moving objects are simulated every 16 ticks (CarMoveSystem.cs:420-423) into a 4-slot TransformFrame ring. ObjectInterpolateSystem.CalculateUpdateFrames renders 32 ticks behind (ObjectInterpolateSystem.cs:4332-4360), which acts as a ready-made jitter buffer.
- RandomSeed (Game.Common/RandomSeed.cs:8) is a static Random seeded from DateTime.Now.Ticks with 196 call sites, including rendering, tools and audio. Jobs use GetRandom(unfilteredChunkIndex). Per-entity seeds exist only partially: Citizen.m_PseudoRandom and PseudoRandomSeed from CreationDefinition.m_RandomSeed. ResourceExporterSystem.cs:473 uses UnityEngine.Random.
- PathfindResultSystem applies results when the worker reaches PathfindActionState.Completed (PathfindResultSystem.cs:208-271). m_ResultFrame is only a deadline (PathfindSetupSystem.cs:427), and PathfindSetupSystem uses Time.deltaTime for spreading (l.326-331).
- WaterSystem.GetTimeStep uses Time.smoothDeltaTime (WaterSystem.cs:1406-1424) with async GPU readbacks. Flood, water damage, pumping, hydro and land value read the water surface data. TerrainSystem CPU heights come from AsyncGPUReadback.
- Time, date and climate are pure functions of frameIndex plus TimeData and climate prefab curves (TimeSystem.cs:89-150, ClimateSystem.cs:607-623), so clients can compute them locally.
- Much authoritative state lives in ISerializable managed system fields: TaxSystem m_TaxRates (92 ints), demand systems, CityStatisticsSystem, Count*, Trade, Production, Electricity/Water statistics. These Serialize/Deserialize methods can be reused for system-state sync.
- Money: PlayerMoney on the City entity is changed by BudgetApplySystem every 256 ticks by (income-expense)/1024 (BudgetApplySystem.cs:30-60). The budget arrays are derived per rendered frame by CityServiceBudgetSystem (ModificationEnd).
- MilestoneSystem (ModificationEnd) adds reward money and Creditworthiness and emits MilestoneReachedEvent and Unlock. DevTreeSystem adds points per MilestoneReachedEvent (DevTreeSystem.cs:30-42). Clients must replicate either the events or the results, never both.
- Zone spawning creates CreationDefinition/ObjectDefinition entities (ZoneSpawnSystem.cs:615-668), the same path as player tools, so the host could forward definitions. Leveling and abandonment come from BuildingUpkeepSystem condition thresholds (l.173-287, 721-728, 481).
- Disabling a system is safe: SystemBase.Update checks Enabled (Unity.Entities/SystemBase.cs:38-70). Producer/consumer NativeQueues must be disabled in pairs to avoid unbounded growth, and Initialize systems (Modification4/5) overwrite fields on newly created entities.
- Estimated 100k city: about 25-60 MB raw of persistent per-entity sim state, 15-35k moving objects, and cell maps of about 1-2 MB. Full movement replication would be about 1-2 MB/s, so interest management is required (around 160 KB/s for 3k visible objects at speed 1).

**Risks**

- Lockstep is infeasible: global wall-clock-seeded RNG shared with rendering and tools, chunk-index-keyed job RNG, 214 parallel NativeQueue writers with thread-order drains, async pathfinding completion, frame-batched command playback, GPU water with a smoothDeltaTime step, and per-machine Entity IDs.
- Entity indices cannot serve as network IDs (local Temp/tool entities), so every Entity reference in replicated components (Worker.m_Workplace, PropertyRenter.m_Property, PathElement targets) must be remapped through a network-ID table, including deferred patching when messages arrive out of order.
- Auto-assigned update offsets depend on the registered system set, so differing mod sets shift system timing between host and clients.
- Event-driven derived state (milestones to dev points and money, XP queues, icons and notifications) can double-apply on clients if both events and results are replicated.
- Disabling a consumer system while producers still run leaks NativeQueue memory without bound. Initialize systems in Modification4/5 can overwrite replicated component values on newly created entities.
- UI and rendering read fields of disabled simulation systems (demand, budget, statistics). These go stale unless refreshed from the host.
- Bandwidth: replicating all moving objects and all per-entity economic state continuously is too expensive (MB/s), so tiered, interest-managed and on-demand replication is mandatory.
- Local pause sources (error dialogs, lightning, photo mode, loading) and the variable host tick rate (CPU and pathfinding back-pressure) must be handled so clients chase the host's frameIndex smoothly.
- Some Modification-phase systems may mutate gameplay state on clients from replicated structural changes (DamageSystem, DestroySystem, ZoneCheckSystem, XPBuiltSystem). Each one needs auditing.

**Open questions**

- Is object, sub-object and sub-net generation from a forwarded CreationDefinition (prefab, transform, m_RandomSeed) fully deterministic on clients? If so, definitions could be replicated instead of the resulting entities.
- Can a mod implement Colossal.Serialization IWriter/IReader for in-memory snapshots of ISerializable system state, and how do Context/version gates behave outside save and load?
- Which Modification-phase systems produce gameplay effects (money, XP, notifications) from structural changes and must be disabled or neutralized on clients?
- Does disabling GameSimulation systems break any UI bindings or containers that rely on their OnUpdate having run at least once?
- What are the real measured entity counts, save size and moving-object counts for a 100k city? A measurement build is needed to finalize bandwidth tiers.
- Is it better to drive the client clock with a Harmony prefix on SimulationSystem.OnUpdate, or to disable SimulationSystem and run a custom driver that sets frameIndex, frameTime and smoothSpeed through reflection?
- Should moving objects be replicated as TransformFrame snapshots (simple, more bandwidth) or as lane state with a client-side cosmetic mover (less bandwidth, custom code)?

## 04-entities-prefabs.md

The game already defines persistent state in code. SerializerSystem.CreateQuery (Game/Game.Serialization/SerializerSystem.cs:171-214) saves every entity that has PrefabRef or LoadedIndex, or one of 16 named singleton/graph types, or any ISerializable/IEmptySerializable component from a non-Game assembly (so mod components are included). It skips Temp, Deleted, NetCompositionData, EffectInstance and LivePath. Each component type is persisted at one of three levels (ComponentSerializerLibrary.cs:25-106): ISerializable writes the data; IEmptySerializable writes only the fact that the component is present, and those values are rebuilt after load (geometry, compositions, every reverse/ownership buffer); all other components are removed from the saved archetype. Game.dll has 788 serializable component types, and 74 systems save global state (tax rates, terrain heightmaps, GPU water/snow textures, custom names, climate, demand, cell maps). Entity handles are renumbered on save and recreated on load, so they are never stable. Some entity indices are hidden in non-Entity fields: PathNode packs owner.Index into a ulong (PathNode.cs:20-49, 133-149), and lanes carry three of these. Prefab identity: PrefabData.m_Index is a position in a list that depends on load order and uses swap-remove, so it differs per machine. The stable key is PrefabID (type name, prefab name, Hash128). The hash comes from the PDX mod platformID, else the asset GUID; prefabs created in code have no valid hash. Saves store only PrefabIDs and re-resolve them on load through ResolvePrefabsSystem and PrefabReferences; prefabs that cannot be resolved become "[Missing]" placeholders. On load, about 40 Deserialize-phase systems rebuild every reverse buffer from forward references, and 94 systems recompute all derived caches through OnGameLoaded. The report ends with a five-tier classification table (authoritative structure, authoritative simulation, saved caches, pure derived, local-only) for every domain, intended to drive the replication design.


**Key findings**

- Save selection query: PrefabRef/LoadedIndex plus 16 explicit types (City, TimeData, ServiceBudgetData, flow-graph nodes/edges, ServiceRequest, CityStatistic, ...) plus all external-assembly serializable components; Temp/Deleted/NetCompositionData/EffectInstance/LivePath excluded (Game/Game.Serialization/SerializerSystem.cs:171-214).
- IEmptySerializable means only the component's presence is saved, not its data (Colossal.Core/.../EmptyComponentSerializer.cs:64-68). This covers EdgeGeometry, NodeGeometry, Composition, ConnectedEdge, SubNet, SubLane, SubObject, SubArea, InstalledUpgrade, Renter, HouseholdCitizen, OwnedVehicle, area Geometry and Triangle, CustomName and Locked. The game itself treats these as derived.
- Non-serializable components are removed from saved archetypes (EntitySerializer.cs:113-136, 479-496); RequiredComponentSystem adds some back on load (e.g. UpdateFrame, Native).
- Entities are renumbered to a dense table on save (EntitySerializer.cs:238-281), so Entity values are never portable. PathNode stores owner.Index inside a ulong (PathNode.cs:20-49), and Lane holds three PathNodes, so lanes hide entity indices.
- PrefabData.m_Index is the index into PrefabSystem.m_Prefabs, assigned in asset-enumeration order (GameManager.cs:1925-1966) and changed by swap-remove in RemovePrefab (PrefabSystem.cs:146-150, 225-256). It differs per machine.
- PrefabID is (type name, prefab name, Hash128). The hash is Hash(platformID) for PDX mods (shared by every asset in the mod), else the asset GUID; prefabs created in code (DuplicatePrefab, ContentPrefab 'Mod:<id>', Anarchy) have no valid hash (PrefabID.cs:15-36). PrefabSystem.TryGetPrefab(PrefabID) is the stable lookup. Duplicate IDs only log a warning and the first registration wins (PrefabSystem.cs:152-172).
- Saving prefab references: BeginPrefabSerializationSystem disables PrefabData on all prefabs, the PrefabReferences phase re-marks every referenced prefab, indices are compacted, only referenced prefab entities are written, and PrefabSystem.Serialize writes the matching PrefabID list (BeginPrefabSerializationSystem.cs:30-192; PrefabSystem.cs:827-865).
- Loading: PrefabSystem.Deserialize puts LoadedIndex on the matching live prefabs; ResolvePrefabsSystem remaps all prefab references, turns unresolved prefabs into obsolete placeholders and destroys the loaded prefab entities (ResolvePrefabsSystem.cs:458-553). The components whose prefab references get remapped are listed in PrimaryPrefabReferencesSystem.cs:392-400.
- Prefab entities hold some city state: unlocks (Locked enable bit), PlacedSignatureBuildingData, and CollectedCityServiceBudget/Fee/UpkeepData (ResolvePrefabsSystem.cs:37-245).
- ZoneType.m_Index in zone Cell/VacantLot is allocated per session (ZoneSystem.cs:176-179) and remapped on load (ResolvePrefabsSystem.cs:252-338). Zoning must go over the wire as a zone PrefabID.
- Reverse buffers are always derived from forward references (Owner, Edge, Attached, PropertyRenter, HouseholdMember, Waypoint, LayoutElement, ...). About 40 systems in SystemUpdatePhase.Deserialize rebuild them (SystemOrder.cs:804-842), and live ReferencesSystems maintain them during play. Replicate forward refs only.
- Lanes are generated by Game.Net.LaneSystem, which reuses existing lane entities matched by LaneKey(Lane PathNodes, prefab, master/slave flags) (LaneSystem.cs:32-67). Lanes are also persisted and referenced by vehicles, paths and routes, so they are derived in topology but need a stable identity.
- Secondary objects (street lights, signs, utility poles) and prefab sub-objects are saved as entities but regenerated by SecondaryObjectSystem and Game.Objects.SubObjectSystem when their owner updates.
- The city entity (no PrefabRef) holds money (PlayerMoney.m_Money is a private field), XP, MilestoneLevel, DevTreePoints, Loan, ServiceFee, Policy and CityModifier (CitySystem.cs:70-135). Budget values live on a standalone ServiceBudgetData entity; tax rates live in TaxSystem system state.
- Map tile ownership is the absence of the Native component (MapTileSystem.cs:142, 229-235; MapTilePurchaseSystem.cs:350). Area polygons are the Game.Areas.Node buffer, which is saved; Geometry and Triangle are derived.
- NameSystem saves custom names as Dictionary<Entity,string> plus a CustomName tag (NameSystem.cs:162, 214-238, 549-580). Generated names are derived from RandomLocalizationIndex, PseudoRandomSeed and addresses.
- 74 systems serialize global state. The authoritative ones include TaxSystem, CityConfigurationSystem (except its camera state), MapTileSystem, GameModeSystem, PlanetarySystem, ClimateSystem, TerrainSystem heightmaps, the TerrainMaterialSystem user splatmap and NameSystem. Simulation-owned ones include SimulationSystem.frameIndex, the Water/Snow GPU textures, wind, groundwater, natural resources and demand. The rest are caches/statistics or local-only (audio, achievements, markers, UI caches).
- OnGameLoaded makes 94 systems (e.g. Net GeometrySystem, GeometrySystem.cs:3382-3406) process all entities once, so a client that joins from a save snapshot gets every derived cache rebuilt by the game itself.

**Risks**

- The simulation is not deterministic across machines: RandomSeed.Next() uses a static Random seeded from DateTime.Now.Ticks (Game/Game.Common/RandomSeed.cs:8-17), and GetRandom(index) is often given chunk indices. Clients cannot keep in sync by simulating locally.
- Entity indices hidden in non-Entity fields (PathNode.m_SearchKey; possibly also in mod components) are missed by a generic pass that only remaps Entity fields.
- Authoritative state lives in GPU textures (water, snow, terrain heightmaps) and needs AsyncGPUReadback(...).WaitForCompletion() to read (WaterSystem.cs:1043, 1063), which is expensive and stalls if done often.
- Reverse buffers are filled in insertion/chunk order, so element order can differ between peers even when the sets are identical. Divergence checks must compare sets, and order-sensitive game logic may still diverge.
- Different mod or asset sets produce missing prefabs (placeholders), duplicate-ID shadowing (first registration wins), and hashless prefabs created in code whose IDs can collide. Swap-remove in RemovePrefab changes prefab indices mid-session.
- Machine-local indices (PrefabData.m_Index, ZoneType.m_Index, UpdateFrame, PathNode owner index) must be translated on the wire; sending one raw corrupts state on the receiver.
- Lanes, generated sub-objects, secondary objects and zone blocks are generated locally yet referenced by identity. Command replay must produce matching keys, or the agents and paths that reference them break.
- High-churn simulation entities (citizens, vehicles, creatures, requests, icons) number in the tens of thousands, so replicating them exactly needs heavy bandwidth or interest management.
- CityConfigurationSystem serializes authoritative options and local camera state together, so they must be split for replication.
- Mod components (ISerializable from external assemblies) are part of saved state, so mismatched mods across peers break convergence.

**Open questions**

- Which prefab-generated sub-objects can also be placed, edited or removed by players or mods (Move It, BetterBulldozer PermanentlyRemovedSubElementPrefab)? This decides whether sub-objects can be treated as derived.
- Are Building.m_RoadEdge, CurrentDistrict, BorderDistrict and the City/District/Building/RouteModifier buffers always recomputed after load or only on update? (Classified as saved caches until verified.)
- Can Icon (notification) entities be fully regenerated on the client from replicated building and simulation state?
- In what order do the tool Apply*Systems create entities, and how deterministically? This is needed so command replay produces matching derived entities.
- Do any built-in prefabs lack an asset and therefore have a hashless PrefabID? To be checked at runtime by dumping PrefabSystem prefab IDs on two machines.
- Can an in-memory SaveGameSystem/LoadGameSystem round trip be used for join and resync snapshots without touching disk or blocking for too long (GPU readbacks)?
- Which other components embed entity indices or session-local indices in plain integer fields, like PathNode and ZoneType do?

## 05-mod-platform.md

The game finds code mods through ExecutableAsset: any top-level type that directly implements IMod qualifies. ModManager loads the DLL from bytes (so Assembly.Location is empty; use modManager.TryGetExecutableAsset to find the mod folder). It then creates every IMod-assignable type with FormatterServices.GetUninitializedObject, so constructors and instance field initializers never run (ModManager.cs:120-123). OnLoad runs once at boot, after SystemOrder.Initialize and before LoadPrefabs/onWorldReady (GameManager.cs:621-635). It can also run later when the user enables a mod at runtime (reinitialize). OnDispose only runs on application quit. UpdateSystem.UpdateAt/UpdateBefore/UpdateAfter sort by phase and then by add index (±1,000,000). Vanilla registers first, and there is no unregister API. MainLoop, Modification, Tool, UIUpdate, Rendering and Pre/PostSimulation run every frame in the main menu, during loading and in game. GameSimulation only runs while the sim actually steps. On loading: onGamePreload fires before Deserialize, OnGameLoaded after it, and onGameLoadingComplete after the loading screen. The first main menu after boot skips preload and deserialize, so a UISystemBase.gameMode filter does not apply there. Navigation from code goes through GameManager.Load(mode, purpose, IAssetData|guid) and MainMenu(). Load has no re-entrancy guard; the vanilla menu queues these calls on TaskManager 'SaveLoadGame' and first sets CityConfigurationSystem/MapMetadataSystem overrides. Settings (ModSetting, AutomaticSettings attributes, LoadSettings/ApplyAndSave keyed by class name), localization (IDictionarySource/MemorySource via LocalizationManager.AddSource, which also feeds cohtml), UI bindings (ValueBinding, GetterValueBinding, RawValueBinding, TriggerBinding, CallBinding, EventBinding), the .mjs UI module header plus ui-mods host plus app.activeUIModsLocation, and the JS moduleRegistry append/extend targets are documented with file:line references. For sync, the key point is that SimulationSystem.selectedSpeed has many local writers: TimeUISystem forced pause via focus loss or the JS 'time.simulationPausedBarrier' subscription, error dialogs, lightning, photo mode, and the loading logic. The number of sim steps per frame also varies by machine. A co-op mod therefore has to re-assert the host's speed every frame in a system registered UpdateBefore SimulationSystem in LateUpdate, and use a host-authoritative model.


**Key findings**

- IMod instances are created with FormatterServices.GetUninitializedObject over all IMod-assignable types (no abstract filter), so constructors and instance field initializers never run (Game/Game.Modding/ModManager.cs:120-123; Colossal.Core/Colossal.Reflection/ReflectionUtils.cs:509-514).
- Mod DLLs are loaded via Assembly.Load(bytes), so Location is empty. The mod folder comes from ModManager.TryGetExecutableAsset(this, out asset).path. Optional '<Name>_win_x86_64' Burst libraries are auto-loaded, and TypeManager.InitializeAdditionalTypes plus SerializerSystem.SetDirty run per mod assembly (ExecutableAsset.cs:229-257; ModManager.cs:147-151, 550-565).
- Boot order: CreateSystems (vanilla SystemOrder), then the mods' OnLoad, then settings.Apply, then LoadPrefabs, then State.WorldReady, then onWorldReady, then MainMenu (GameManager.cs:611-660). OnLoad can also run at runtime on playset change (GameManager.cs:1644). OnDispose only runs on quit (GameManager.cs:802).
- UpdateSystem: UpdateAt = ++addIndex, UpdateBefore = -1e6, UpdateAfter = +1e6. Sorting is by phase, then addIndex. UpdateBefore<T,Other>/UpdateAfter<T,Other> place relative to a specific system. There is no unregister. A mod's UpdateBefore(LateUpdate) runs before SimulationSystem (UpdateSystem.cs:158-181; SystemOrder.cs:47-77).
- World phases run whenever State >= WorldReady, which includes State.Loading. PreSimulation/PostSimulation run every frame even when paused and in the menu. GameSimulation runs only when steps > 0 and ToolSystem.actionMode.IsGame() (GameManager.cs:296, 2401-2426; SimulationSystem.cs:270-296).
- Load sequence: gameMode is set at load start, then onGamePreload, then the Deserialize phase, then OnGameLoaded, then the loading screen, then onGameLoadingComplete and State.WorldReady. The first boot main menu skips preload and deserialize, so UISystemBase.gameMode gating is not applied until the first load or exit (GameManager.cs:1053-1152; UISystemBase.cs:60-64).
- GameManager.Load(mode, purpose, IAssetData|Hash128) and MainMenu() are public. Load has no re-entrancy guard. The vanilla menu uses TaskManager.EnqueueTask("SaveLoadGame", ..., 1) and sets MapMetadataSystem, CityConfigurationSystem.overrideLoadedOptions and GameModeSystem.overrideMode first. overrideLoadedOptions=false makes all city options come from the save (MenuUISystem.cs:716-815, 1071-1086; CityConfigurationSystem.cs:423-438).
- GameManager.Save sets userState.lastSaveGameMetadata (the Continue button) on success. AutoSaveSystem saves periodically in Game mode when general.autoSave is on, so clients need this suppressed (GameManager.cs:995-999; AutoSaveSystem.cs:68-160).
- ModSetting.id = Assembly.Namespace.ModType. Its locale key helpers are documented. Setting.ApplyAndSave saves via SaveSpecificSetting(GetType().Name), so the settings class name must be unique. LoadSettings writes into the existing instance and creates the [FileLocation] .coc file when none exists (ModSetting.cs:36-371; Setting.cs:151-161; AssetDatabase.cs:613-666, 792-830).
- In AutomaticSettings, a property without the needed attribute (e.g. int/float without a slider) gets no widget. The setter attribute method is invoked before the property is assigned, then ApplyAndSave runs. Hide/Disable/ValueVersion conditions are live, but the page structure is built once at RegisterSetting (AutomaticSettings.cs:423-517, 1049-1213; OptionsUISystem.cs:621-648).
- UI module: a .mjs whose header contains 'Cities: Skylines II UI Module' plus Id/Author/Version/Dependencies. Its folder is added as host 'ui-mods' and coui://ui-mods/<file> is pushed through binding app.activeUIModsLocation. The JS default export register(moduleRegistry) uses append('Menu'|'Game'|'GameTopLeft'|...) and extend/override (UIModuleAsset.cs:27-110; ModManager.cs:464-496; thirdparty modding.d.ts:4-22).
- Binding semantics: GetterValueBinding polls only while observed and must be added via AddUpdateBinding. ValueBinding pushes on change. TriggerBinding/CallBinding carry JS-to-C# calls. EventBinding.observerCount can act as a barrier. UISystemBase systems belong in SystemUpdatePhase.UIUpdate, which also runs in the main menu.
- SimulationSystem.selectedSpeed (0 = paused) has the following local writers: TimeUISystem (UI triggers, forced pause on focus loss or JS subscription to time.simulationPausedBarrier), ErrorDialogManager (pauses on error dialogs), ClimateRenderSystem (lightning), PhotoModeRenderSystem, and the loading logic (setter ignored while loading; pausedAfterLoading). Steps per frame depend on deltaTime, pathfinding backlog and performancePreference, capped at 2/4/8 per frame (SimulationSystem.cs:72-85, 155-296; TimeUISystem.cs:93-142, 205-240).
- NotificationSystem.Push/Pop (static) gives toasts in all modes, with progress states. appBindings.ShowConfirmationDialog/ShowMessageDialog have a single callback slot. Chirps are simulated, saved ECS entities and are unsuitable for chat (NotificationSystem.cs:22-35; AppBindings.cs:380-404; ChirperUISystem.cs:79-125).
- A focused cohtml text input sets InputManager.hasInputFieldFocus, which masks keyboard devices out of the active mask, so a chat textbox will not trigger hotkeys. Mod hotkeys are ProxyBinding properties on ModSetting plus RegisterKeyBindings, then GetAction(name) and shouldBeEnabled (UserInterface.cs:168-171; InputManager.cs:644-651; ModSetting.cs:141-292).

**Risks**

- Simulation stepping is not deterministic across machines: steps per frame depend on deltaTime, PathfindResultSystem pending frames and the performancePreference setting. Lockstep by speed alone cannot keep clients tick-aligned, so a host-authoritative design is needed.
- Many independent local writers of selectedSpeed (forced pause barrier, error dialogs, lightning, photo mode, loading) mean the speed must be re-asserted every frame before SimulationSystem, or clients will drift or pause unilaterally.
- UpdateSystem.Refresh auto-assigns interval offsets cumulatively across interval groups. A different mod set or registration order can shift when vanilla interval systems run in GameSimulation, so identical mod sets are required.
- GameManager.Load has no re-entrancy guard. Concurrent load requests (e.g. a network-driven load while the user clicks the menu) can corrupt flow unless they are serialized on the SaveLoadGame task queue.
- OnDispose only runs on quit and OnLoad can run mid-session on a playset change, so session teardown must hook the game lifecycle (OnGamePreload Cleanup/MainMenu), not the mod lifecycle.
- GetUninitializedObject instantiation silently leaves instance fields null and fails on abstract IMod types or on GetTypes() load exceptions. A mod-entry bug would disable the whole mod.
- GameManager.Save and AutoSaveSystem mutate user state (lastSaveGameMetadata, autosave files) on clients if not suppressed.
- The UISystemBase gameMode gating is not applied in the first main menu after boot, so game-only UI systems may be active in the menu.
- Single-slot dialog callbacks in AppBindings: overlapping dialogs from the mod and vanilla overwrite each other's callbacks.
- Pause-menu and time-control JS module paths and the subscribers of the simulationPausedBarrier binding are not visible in C#. UI extension points for these must be discovered at runtime and may change with game updates.

**Open questions**

- Exact JS module paths and export names of the pause menu and time-controls components, needed for moduleRegistry.extend/override (requires -uiDeveloperMode inspection).
- Which vanilla JS components subscribe to time.simulationPausedBarrier (pause menu, options, tutorials?), and therefore when the single-player forced pause kicks in.
- Whether any PC platform integration fires AppState.Constrained. No IAppStateSupport implementer was found in the decompiled Steam/PDX PSI assemblies.
- Best way to load a host-sent save without touching disk: public Load needs IAssetData and the descriptor overload is private. Is a transient ILocalAssetDatabase (as used by Save) sufficient? This belongs in the serialization report.
- Semantics of the 'UniversalModMenu' append target declared in the community typings.
- Whether clients should run GameSimulation at all (paced by host frameIndex targets) or stay paused and only apply replicated state. This depends on the replication reports.

## 06-network-platform.md

On the Steam build, the game sets up SteamAPI under app ID 949230 (SteamworksPlatform via PlatformSupport.kCreateSteamPlatform) before any mod's IMod.OnLoad runs. If that setup fails, the game quits, so a running game always has Steam up. SteamAPI.RunCallbacks is called once per frame on the main thread from GameManager.Update, after the ECS MainLoop and Cleanup phases. It keeps running during loading and shutdown, and IMod.OnDispose runs before Steam shuts down. Steamworks.NET 20.2.0 / SDK 1.57 uses Steam's manual-dispatch mode with a list of subscribers per callback. That makes it safe for a mod to create its own Callback<T> and CallResult<T>, as long as it keeps references to them, uses the game's Steamworks.NET DLL, and never ships a second Steam wrapper. The game itself uses no Steam networking, lobbies or join requests, so the mod owns those, starting with a call to InitRelayNetworkAccess. Recommended transport: Steam Networking Sockets P2P (ConnectP2P / CreateListenSocketP2P plus a poll group). It provides the Steam relay for NAT traversal, built-in encryption, and reliable and unreliable messages. Snapshots must be split into chunks because messages are capped at 512 KiB, and the snapshot needs its own lane or a second connection so it does not block commands. The Steamworks.NET binding for lanes is broken, so lanes need custom P/Invoke. Saves are already ZSTD-compressed; the game ships native LZ4/ZSTD (CompressionUtils/NativeCompression) and System.IO.Hashing XxHash for integrity checks. System.Net.Sockets works under Mono 4.6.57 (the game itself uses Dns and Ping), but ECS thread checks are compiled out of the player, so all ECS writes must go through a main-thread queue (MainThreadDispatcher is unordered). Non-Steam stores have no Steam relay; the GDK wrapper ships but this Game.dll does not use it.


**Key findings**

- SteamAPI is set up before mods load (GameManager.cs:593, then mods at :624); app ID 949230 is hard-coded at Game.PSI/PlatformSupport.cs:10-12; if setup fails the game quits (GameManager.cs:1678-1682).
- RunCallbacks is called every frame on the main thread: GameManager.Update:724 -> PlatformManager.Update (PlatformManager.cs:690-707) -> SteamworksPlatform.Update:587. It runs after the ECS MainLoop and Cleanup phases and outside the shouldUpdateManager guard.
- CallbackDispatcher uses manual dispatch (CallbackDispatcher.cs:35) and keeps a list of subscribers per callback ID (:10, :56-69), copies the list before dispatch (:190-192) and catches exceptions per handler, so a mod can safely add its own Callback<T>. Callback<T> and CallResult<T> unregister when garbage-collected (Callback.cs:46, CallResult.cs:36), so the mod must keep references to them.
- steam_api64 refuses a second dispatch mode (string: 'standard dispatch has already been selected'), so the mod must reference the game's com.rlabrecque.steamworks.net.dll and never ship its own Steamworks wrapper.
- The game never uses SteamNetworkingSockets/Messages, SteamMatchmaking, InitRelayNetworkAccess, or the GameLobbyJoinRequested / GameRichPresenceJoinRequested callbacks (grep is empty).
- Steam Networking Sockets v012 API is fully present: ConnectP2P, CreateListenSocketP2P, poll groups, ReceiveMessagesOnPollGroup, GetConnectionRealTimeStatus, CreateSocketPair, and Fake* network-simulation config values. Max message size is 524288 bytes (Constants.cs:253); send flags are at Constants.cs:255-271.
- Binding defects: ConfigureConnectionLanes uses 'out int / out ushort' instead of arrays (SteamNetworkingSockets.cs:138, NativeMethods.cs:2075), and SendMessages passes structs by value (NativeMethods.cs:2048). Both need custom DllImport; the flat exports SteamAPI_SteamNetworkingSockets_SteamAPI_v012 and SteamAPI_ISteamNetworkingSockets_ConfigureConnectionLanes are present.
- The game overwrites Steam rich presence (steam_display plus 7 other keys) every 5 seconds (RichPresenceUpdateSystem.cs:306-325). The mod can still use the 'connect' and 'steam_player_group' keys (30-key limit, Constants.cs:81).
- Saves are serialized with BufferFormat.CompressedZStd (SerializerSystem.cs:102). Native LZ4/ZSTD is available via Colossal.Compression.CompressionUtils, and System.IO.Hashing 9.0 provides XxHash3/XxHash128.
- Mono 4.6.57 / netstandard 2.1: System.Net.Sockets, SslStream and HttpClient are present, and the game itself uses Dns and Ping (Connectivity.cs:73-113). BrotliStream is likely broken (no Brotli in MonoPosixHelper); whether AesGcm and ECDH work is uncertain.
- ECS main-thread asserts are marked [Conditional(ENABLE_UNITY_COLLECTIONS_CHECKS)] and compiled out (EntityDataAccess.cs:331-339), so threading bugs corrupt state silently. MainThreadDispatcher.RunOnMainThread stores actions in an unordered ConcurrentDictionary and logs every call, so it is unsuitable for per-message dispatch.
- PDX SDK supports mod parity checks: GetModsInActivePlayset (PdxSdkPlatform.cs:1614) and SubscribeAll(List<string>) (:1753). DLC ownership can be checked with PlatformManager.IsDlcOwned.
- boot.config has single-instance= (two clients cannot run on one PC) and gc-max-time-slice=3 (incremental GC: avoid allocating per network message).
- The GDK (XblMultiplayer and related) ships in this install but this Game.dll does not use it (only Steam and Discord are registered). Discord's Game SDK lobby and network features are present but deprecated and tied to Colossal Order's Discord client ID.

**Risks**

- Without lanes or a second connection, a 20-300 MB reliable snapshot transfer blocks all reliable commands queued behind it on the same connection; the Steamworks.NET lanes binding is broken, so this needs custom P/Invoke.
- Steam relay throughput is unknown and variable, so joining a large city may take minutes; transport tuning alone may not fix this, and making the snapshot smaller may be needed.
- Callbacks are pumped once per frame on the main thread, so in large cities connection and lobby events arrive 33-50 ms late; message polling has to be done separately.
- ECS safety checks are compiled out, so any off-main-thread ECS access corrupts the world silently instead of throwing.
- A game patch could change the Steamworks.NET or SDK version and break the custom DllImports (flat accessor _v012) or the struct layouts.
- Non-Steam stores (Game Pass) have no Steam relay or lobbies; cross-store play needs a third-party relay (for example EOS) plus its own identity and credentials.
- The Paradox Launcher may drop Steam's +connect_lobby argument when a friend joins while the game is not running, which would break 'Join Game' from the Steam friends list in that case.
- The game rewrites steam_display every 5 seconds, so the Steam friends list cannot show custom co-op status text.
- Unity single-instance mode blocks running two clients on one PC; real P2P testing needs two machines or two Steam accounts.
- If the host's game does not run in the background, alt-tabbing the host would stall the simulation for everyone.

**Open questions**

- Does 'Join Game' from the Steam friends list reach Cities2.exe with +connect_lobby when the game is not already running, or does the Paradox Launcher drop it?
- What are the default SendRateMin, SendRateMax, SendBufferSize and P2P_Transport_ICE_Enable values in this steam_api64 build? Query them with GetConfigValue.
- What sustained throughput does the Steam relay give for typical friend pairs, and how often do direct (ICE) connections succeed?
- Is Application.runInBackground enabled in the player settings? No game code sets it.
- Do AesGcm and ECDiffieHellmanCng work under this Mono build? This only matters for a non-Steam fallback.
- On the Game Pass build: which platform integrations are registered, do code mods load, and can a mod access the Xbox identity?
- Can the game's save loader load a snapshot from a temporary file without registering it as a user save? To be covered by the serialization research.

## 07-terrain-water.md

Terrain is stored in one 4096x4096 R16_UNorm GPU texture, TerrainSystem.m_Heightmap. It covers the 14336 m playable area, so each texel is 3.5 m and each height step is about 0.0625 m. It is the only terrain state that is saved, and it changes only through SetHeightmap (load or replace) and brush application (ApplyToTerrain). Roads, building lots and terrain areas are not baked into it: every update they are drawn into a separate 4-slice cascade texture. The CPU height array that simulation, snapping and GroundHeightSystem read (GetHeightData/TerrainUtils) is copied back from that cascade asynchronously. Terraforming is a chain of tools and systems: TerrainToolSystem creates a BrushDefinition using Time.deltaTime, GenerateBrushesSystem splits each mouse movement into Temp Brush stamps, and ApplyBrushesSystem passes them to TerrainSystem.ApplyBrush. ApplyBrush uses Time.unscaledDeltaTime, clamped to at least 0.05, and runs the AdjustTerrain GPU compute shader. Because of the frame-time inputs, replaying mouse input will diverge between machines. Replaying the captured Brush structs with a pinned delta gives the same inputs, but cross-GPU bit-exactness cannot be verified, so the authoritative path should be transferring dirty tiles of m_Heightmap, checked by hashes. The game has no terraform undo, and brush entities are temporary and never saved. Water is a GPU simulation on a 2048x2048 RGBA32F texture (depth, velocity x/y, pollution). It steps once per rendered frame from RenderPipelineManager.beginFrameRendering, with a timestep based on smoothDeltaTime and on which tiles are currently active. So it is inherently non-deterministic across machines, and its CPU copy is refreshed one 256x256 tile at a time. WaterTexture is a public RenderTexture, so the host can read it back and send tiled snapshots, and clients can write those regions back into it. Gameplay that depends on water (pumping, floods, water damage, soil water, placement validation) must run only on the host. Snow is a GPU simulation driven by simulation ticks and only affects visuals. The cell-map systems are small CPU arrays that affect gameplay; several use RandomSeed, which is seeded from DateTime.Now.Ticks, so the host must send snapshots of them.


**Key findings**

- TerrainSystem.m_Heightmap (R16_UNorm 4096^2, enableRandomWrite) is the only saved terrain state (Serialize 3079-3095). The cascade, objects layer and downscaled map are derived and rebuilt from ECS state (lots, net lanes, areas) by RenderCascades (4442-4514).
- The CPU heights (m_CPUHeights) are an async GPU readback of the cascade slice baseLod (3624, 3672), so they include roads and lots. TerrainUtils.SampleHeight reads them, and the latency depends on frame timing.
- Brush pipeline: TerrainToolSystem.UpdateDefinitions (m_Time = Time.deltaTime, line 709) -> GenerateBrushesSystem (stamp count = 1+floor(len/(size*0.25)), strength depends on m_Time, lines 78-109) -> ApplyBrushesSystem (Temp+Brush, ApplyTool phase, 245-314) -> TerrainSystem.ApplyBrush (Time.unscaledDeltaTime, 3976) -> ApplyToTerrain GPU compute (AdjustTerrain kernels, 3741-3962).
- ApplyToTerrain clamps delta to at least 0.05 (line 3774), so at >=20 fps only Brush.m_Strength varies; capturing final Brush structs on the host gives identical inputs. Brush.m_Opacity is not used by ApplyToTerrain or by ApplyCellMapBrushJob.
- There is no terraform undo in the game. Brush entities get Applied+Deleted right away and are never saved.
- Public hooks for writing heightmap tiles on clients: TerrainSystem.heightmap (the RenderTexture, for CopyTexture), OnAreaChanged(Bounds2), UpdateMinMax(Brush, Bounds2), TriggerAsyncChange(), and WaterSystem.TerrainWillChangeFromBrush(Bounds2). ReplaceHeightmap(Texture2D) is available for full replacement.
- GroundHeightSystem.UpdateHeightsJob rewrites Transform/Curve/Node heights from local CPU terrain and water whenever the change is >=0.01 m (around lines 587-640). Clients must suppress this or let host-replicated transforms override it.
- The water GPU sim runs per rendered frame via UpdateSystem.OnBeginFrame -> WaterSystem.OnSimulateGPU -> Simulate (1461-1577). GetTimeStep (1406-1425) uses Time.smoothDeltaTime with lerp smoothing, and active tiles come from async readbacks, so it is not deterministic.
- WaterTexture = waterTextures[0], public RenderTexture 2048^2 R32G32B32A32_SFloat; channels: x depth, yz velocity, w pollution. Saved via a synchronous readback (Serialize 1030-1070) and loaded via LoadWaterData (internal, compute Load kernel, WaterSimulation.cs 468-499).
- The CPU water copy (SurfaceDataReader, internal) is refreshed one 256x256 tile (of 64) every 30 water frames (BaseDataReader 136-192, CheckReadbacks 1427-1447). It is a stale mosaic.
- Water sources are ECS entities, Game.Simulation.WaterSourceData plus Transform. Sewage outlets and pumping stations set m_Height and m_Polluted from the simulation. The legacy (river/sea, tsunami-affected) and new (sea level global, Modifier) paths differ (WaterSimulation.SourceJob 25-82 vs WaterSimulationLegacy.SourceJobLegacy 19-100).
- SnowSystem is GPU (1024^2 R16G16), runs every 4 sim ticks with a fixed 0.2 timestep, reads the water texture, terrain and sun direction, and has only rendering consumers. It is cosmetic.
- CellMapSystem<T> maps are public NativeArrays (GetMap/AddWriter), sized 64^2-256^2 with infrequent updates. Air/Ground pollution and NaturalResource use RandomSeed.Next(), which is seeded from DateTime.Now.Ticks (RandomSeed.cs line 8). SoilWaterSystem reads CPU water and starts and stops flood events, so it must be host-only.

**Risks**

- Terraforming results depend on frame timing (Time.deltaTime in the tool, Time.unscaledDeltaTime in ApplyBrush, stamp count depends on mouse movement per frame), so input replay cannot converge.
- The GPU compute shaders (AdjustTerrain, the water update shader, snow) and the cascade raster shaders are not in the decompiled code. Bit-exactness across GPU vendors and drivers is unknown, so even exact Brush replay may differ by about 1 LSB.
- The water simulation is stepped per rendered frame with a smoothed, frame-time-dependent timestep and readback-driven active-tile culling. It is fundamentally non-deterministic, so only snapshots can make it identical.
- Water snapshots are large (64 MiB raw for the full main texture, 16 MiB for the backdrop). The game's own Serialize path uses synchronous WaitForCompletion readbacks that would stall the host, so a mod needs async tiled readbacks and quantisation.
- Important write paths are private or internal (ApplyToTerrain, m_LastWrite, SurfaceDataReader.LoadData, WaterSimulation.LoadWaterData, ResetActive). They need reflection or Harmony and can break on game patches.
- GroundHeightSystem on clients re-snaps object, net and area heights from local CPU heights and water, using a 0.01 m threshold smaller than one height step (about 0.0625 m), which can fight host-replicated transforms.
- Cell-map simulations use a DateTime-seeded RNG, and SoilWaterSystem creates flood event entities from non-deterministic water. Running them on clients would cause divergence.
- Third-party mods (for example Water_Features) change water parameters and sources at runtime. Peers need the same mods and settings, or the host must replicate those values.
- CPU height and water readbacks arrive several frames late, so client-side tool previews and validation may use stale data. Placement validity must be decided by the host.

**Open questions**

- What does the AdjustTerrain compute shader do with _WaterTexture? Does terraforming behaviour depend on local water state? The shader source was not available.
- Are the terrain brush kernels and the cascade raster bit-identical between NVIDIA, AMD and Intel GPUs with the same inputs? This needs an empirical test: hash m_Heightmap after replaying the same Brush list on different GPUs.
- Is Graphics.CopyTexture into WaterTexture enough for the water sim to accept new state, or must the internal Load kernel path and ResetActive/sea propagation also run? This needs an in-game test.
- What is the best snapshot cadence and quantisation for water that keeps visuals good while staying within bandwidth? Tile size, round-robin vs change-driven, and float16 vs ushort depth all need measuring.
- Should clients run their own water sim for smooth visuals and accept drift between snapshots, or freeze it (WaterSimSpeed=0) and show only host snapshots? This is a UX trade-off.
- Does any code path create permanent (non-Temp) Brush entities via CreationFlags.Permanent? ApplyBrushesSystem only queries Temp brushes, so such brushes would never be applied.
- How should material painting (TerrainMaterialSystem user splatmaps, GPU, saved) be synced: by tile transfer or by stamp replay?

## 08-ecs-change-detection.md

The game ships Unity Entities 1.0.x. The version is inferred from the API surface (obsolete overloads marked "RemovedAfter Entities 1.0", the 1.0 IJobChunk signature, query fields Present and Absent); the DLL version reads 0.0.0.0. Safety checks are stripped from this build, so nothing stops races with running game jobs; the replicator must complete job dependencies itself. Everything a generic replicator needs is public: DynamicComponentTypeHandle, ArchetypeChunk.GetChangeVersion/DidChange/GetOrderVersion/SequenceNumber, GetDynamicComponentDataArrayReinterpret<byte>, GetUntypedBufferAccessor, GetEnableableBits, TypeManager.GetTypeInfo/GetEntityOffsets/GetTypeIndexFromStableTypeHash, and EntityArchetype.StableHash. Only the EntityManager.*Raw* helpers and the ECB Unsafe* raw methods are internal. Change versions are tracked per chunk and per component type, and they record RW access, not actual writes. CS2 jobs take RW handles over whole UpdateFrame slices, so version checks are only a coarse filter and must be followed by a byte comparison against a shadow copy. Unity's own EntityDiffer works the same way, though in this build its ChunksAreDifferent simply returns true. Entities move between chunks constantly, because the game adds and removes Updated/Created/BatchesUpdated tags every frame and removals swap the last entity into the hole. The shadow copy therefore has to be keyed per entity, not by chunk position. The game detects changes mainly through those tag components, cleared by PrepareCleanUpSystem and CleanUpSystem; change filters, order versions and LastSystemVersion are used only in a few places, and ArchetypeChunk.DidChange never. Entity indices are reused aggressively and versions are local to each process, so a network-id layer is required. I recommend a dense side table indexed by Entity.Index with a version check, which is the same pattern the game's save serializer uses. Adding a data-carrying NetId component to game entities is not an in-place operation: it forces every entity to be copied into new chunks, and the component would be stripped from saves anyway. The report contains the full sender/receiver recipe, with per-chunk version-equality tests, per-entity memcmp, Entity remapping through TypeInfo entity offsets, untyped buffers, enabled bits, batched structural changes and xxHash3 convergence checks, plus cost estimates. CPU cost is about 1-3 ms per tick single-threaded in Burst for about 1M entities, but Burst is mandatory. Bandwidth, not CPU, is the real limit.


**Key findings**

- Entities 1.0.x is inferred from the API surface (obsolete 'RemovedAfter Entities 1.0' overloads, the 1.0 IJobChunk signature, EntityQueryDesc Present/Absent). This is a release build with safety checks stripped (UE/DynamicComponentTypeHandle.cs:9-27), so the replicator must call EntityQuery.CompleteDependency or chain job dependencies itself.
- Mods can ship Burst code: ExecutableAsset loads *_win_x86_64 libraries via BurstRuntime.LoadAdditionalLibrary (Colossal.IO.AssetDatabase/.../ExecutableAsset.cs:249-256).
- Chunk change versions are stamped by any RW access path (ChunkDataUtility.cs:171-261), including RW GetNativeArray, ComponentLookup writes and enabled-bit writes. DidChange is a wrap-safe signed difference and returns true when requiredVersion is 0 (ChangeVersionUtility.cs:7-23). The order version is the change version of column 0 (ArchetypeChunkData.cs:240-260).
- SystemBase advances GlobalSystemVersion only for systems that actually run (SystemState.cs:351-365, SystemBase.cs:38-80). Query change filters allow at most 2 types and are OR-ed (EntityQueryImpl.cs:741-784, MatchingArchetype.cs:130-158), and they can only be baselined to the owning system's LastSystemVersion. The replicator should therefore do its own per-chunk tests.
- Structural moves: Allocate stamps all columns plus the order version (ChunkDataUtility.cs:751-767). Remove swaps the last entity into the hole and stamps only the order version (769-813). In-place archetype change happens only when layouts are compatible, i.e. zero-sized tags or shared components (630-648, EntityComponentStore.cs:3380-3395).
- The game detects changes mainly through tag components (Created/Updated/Deleted/Applied/BatchesUpdated/EffectsUpdated/PathfindUpdated), removed in the Cleanup phase by CleanUpSystem (Game.Common/CleanUpSystem.cs:24-56, PrepareCleanUpSystem.cs:23-52). There are few SetChangedVersionFilter uses (CountHouseholdDataSystem.cs:1042, ChirperUISystem.cs:103-104), GetComponentOrderVersion appears in UI systems, LastSystemVersion in BatchDataSystem.cs:2570-2638, and ArchetypeChunk.DidChange is never used. 54 jobs early-return on the UpdateFrame slice before taking RW arrays.
- Runtime typing: TypeManager.GetTypeIndex(Type), ComponentType.ReadOnly(Type/TypeIndex), TypeInfo (SizeInChunk, ElementSize, EntityOffsetCount, StableTypeHash), and TypeManager.GetEntityOffsets(typeIndex, out count) are all public (TypeManager.cs:111-235, 882-893, 961-970). StableTypeHash hashes namespace, name, assembly and the field layout recursively (TypeHash.cs:57-149); resolve it with GetTypeIndexFromStableTypeHash (TypeManager.cs:1683-1694). EntityArchetype.StableHash combines member type hashes (EntityComponentStore.cs:2372-2381).
- TypeIndex is process-local: mod types are appended at load through ModManager.AfterLoadAssembly -> TypeManager.InitializeAdditionalTypes (ModManager.cs:147-151).
- Untyped access: GetDynamicComponentDataArrayReinterpret<byte> (ArchetypeChunk.cs:730-744), GetUntypedBufferAccessor (817-835) with ResizeUninitialized (UnsafeUntypedBufferAccessor.cs:95-100), GetEnableableBits (302-317). Buffer chunk columns contain a process-local BufferHeader pointer (BufferHeader.cs:9-38) and must never be sent raw. ClearEntityReferences (ChunkDataUtility.cs:1257-1319) is the canonical template for walking Entity fields in components and buffers.
- EntityManager.GetComponentDataRawRO/RW, SetComponentDataRaw and GetBufferRawRO/RW are internal (EntityManager.cs:2730-2797); ECB UnsafeAddComponent/UnsafeSetComponent are internal too. Every EntityManager structural change completes all jobs (EntityDataAccess.cs:391-407).
- Entity allocator: 8192-slot blocks, takes the first free bit, version incremented on allocation and on destruction, odd version means alive (EntityComponentStore.cs:660-674, 720-804, 857-875). Indices are reused immediately, so a NetId layer is mandatory. GetCreatedAndDestroyedEntities copies and sorts all entities on every call (EntityComponentStore.cs:5496-5531), which makes it debug-only.
- Cleanup components keep a destroyed entity alive as cleanup residue (EntityComponentStore.cs:4386-4424). The save serializer strips archetype types that have no serializer (EntitySerializer.cs:96-136) and remaps entities through a dense table indexed by Entity.Index (EntitySerializer.cs:238-282, EntityDeserializer.cs:482-538).
- Unity's EntityManagerDiffer/EntityDiffer works by matching chunks on SequenceNumber, skipping components whose chunk versions are equal, then memcmp (EntityDiffer.cs:102-190, 991-999, 1231-1241). In this build ChunksAreDifferent returns true (EntityDiffer.cs:192-195), and the differ needs EntityGuid on every entity plus a full shadow world, so we should copy its design rather than use it.
- Recipe: sender queries with RO handles only; per-chunk records keyed by SequenceNumber hold the order version and per-type versions, compared for equality; changed chunks are memcmp'd per entity against a shadow keyed by net slot; payload Entity fields are rewritten to tagged NetRefs (Net/Prefab/Null/Local) via the TypeInfo entity offsets. The receiver does one structural batch per tick (CreateEntity(archetype, n), batched destroy and add/remove), then writes bytes directly into chunks with RW dynamic handles, remaps entities, defers unresolved refs and sets enabled bits. Rotating xxHash3 slice hashes check convergence.
- Cost estimate for about 1M entities, 25k chunks and 8 types: version checks about 1 ms Burst single-threaded (10-15 ms in Mono), false-positive scanning 1.5-3 ms single-threaded or about 0.3 ms parallel, shadow memory 30-100 MB. Bandwidth (tens of MB/s if motion were replicated raw) is the real limit.

**Risks**

- Using an RW handle on the sender stamps change versions and corrupts detection for us and for game systems that use change filters.
- Chunk churn from per-frame tag add/remove and swap-back removal breaks any shadow keyed by chunk position; the shadow must be keyed per entity.
- Safety checks are stripped, so races between our reads or writes and running game jobs fail silently.
- Entity values hidden inside fixed buffers, pointers or opaque FixedBytes/FixedList do not appear in TypeInfo entity offsets and would be copied raw.
- Prefab entities are created per machine, so every Entity field pointing at a prefab needs prefab-id remapping through PrefabSystem.
- Raw byte copying requires identical struct layouts, i.e. the same game version and mod set; this must be enforced in the handshake via StableTypeHash and sizes.
- Game systems on the receiver can overwrite replicated components between deltas and cause divergence; they need gating, and hash checks only detect the problem.
- Receiver structural changes are global sync points (complete all jobs); if they are not batched once per tick they cost frame time.
- Adding a data-carrying NetId component to game entities forces copying every entity into new chunks, and the component is stripped from saves.
- GlobalSystemVersion wraps after many hours; DidChange against old baselines then gives wrong answers, so use per-chunk version equality instead.
- Bandwidth: replicating frequently changing or motion state raw is infeasible over Steam P2P; this needs strict type selection, rate caps and XOR-delta plus compression (no liblz4 ships with the game; Unity's LZ4 codec service is internal).
- Applying bytes on the receiver does not trigger the game's reactive systems unless Updated/BatchesUpdated tags are added, and adding tags is itself a structural change.

**Open questions**

- What is the exact Entities patch version? (The 1.0.x API surface was verified directly; the DLL file version reads 0.0.0.0.)
- Which CS2 components are authoritative state and which are derived and recomputed by game systems? This decides the replicated set and whether the receiver must add Updated tags.
- Can the join-time bootstrap 'NetId = save serialized index' be made reliable using the private entity tables in EntitySerializer and EntityDeserializer?
- What are the real entity, chunk and archetype counts in large saves, and what fraction of chunks gets stamped per tick for each candidate type? This needs in-game measurement before fixing the budgets.
- Do any vanilla candidate types hide Entity values inside FixedList or fixed storage?
- Where should the replicator system sit in the update order (after ModificationEnd and before Cleanup is assumed), and how does it interact with the SafeCommandBufferSystem barriers?
- Does Mono enforce access checks when internal Entities methods are called through a publicized reference assembly, or is reflection required?

## 09-third-party-mods.md

All 10 mods with local source change world state. Most of them do it outside the vanilla Temp/definition pipeline. MoveIt changes Transform, Node, Curve, area nodes and Elevation directly. Tree Controller's brush changes tree state, swaps PrefabRef in place and toggles enabled bits, again directly. Better Bulldozer, Water Features' water tool and Zoning Toolkit's tool also write straight to persistent entities. So does Anarchy's components tool, plus the settings buttons of several mods. Several mods run enforcement or derivation systems on every machine that would fight replicated state. Examples are Anarchy's ResetTransformSystem and the Overridden-removal systems, Plop the Growables' PloppedBuildingSystem and its replacement zone check, and Tree Controller's growth pause in the Rendering phase. Better Bulldozer's frame-counted deletions and Zoning Toolkit's block resizing in Modification4B are further cases. Several mods also mutate the world at load time using the joining player's local settings (529 Tiles PostDeserialize, Historical Start, Plop's ExistingBuildingSystem, Anarchy and Better Bulldozer load hooks). The game's save system automatically includes every mod ISerializable/IEmptySerializable component in its entity query (ComponentSerializerLibrary.cs:45-98, SerializerSystem.cs:171-209). It also saves enabled bits of enableable components, so the save query is the right basis for generic persistence tracking. However, some persistent entities have no PrefabRef (water sources, Better Bulldozer record entities), MoveIt creates PrefabRef(Entity.Null) control-point entities, and some mod components hold Entity references (Better Bulldozer, Traffic). Design A (generic final-state replication) covers all of this if four conditions hold. It must track identity without PrefabRef, remap Entity fields, replicate enabled bits and archetype/PrefabRef changes, apply change-sets atomically before ModificationEnd, filter local churn (Highlighted, Updated, BatchesUpdated), and suppress the per-machine mod systems on clients. Design B (intent replay) is fundamentally incomplete for this mod set, because of the many direct writes. Anarchy's post-apply processing also keys on the local active tool, and Line Tool uses random seeds that re-roll over time. Traffic disables the vanilla LaneSystem and replaces it, so it and most of these mods must be installed at the same version on all peers. A session-settings channel and a prefab-unlock channel are also needed.


**Key findings**

- [V] Mod components implementing ISerializable/IEmptySerializable are auto-registered and saved. The save query is Any(PrefabRef, WaterSourceData, ..., all mod serializables) minus Temp/Deleted/NetCompositionData (Colossal.Core/.../ComponentSerializerLibrary.cs:45-98; Game/Game.Serialization/SerializerSystem.cs:171-209). Enableable empty components such as Decoration, LumberResource and Locked are saved with their enabled bit.
- [V] Updated, BatchesUpdated, Highlighted and Temp are not serializable. ZoningToolkit, BetterBulldozer and Anarchy tools write Highlighted onto persistent entities, and Anarchy PreventCullingSystem adds camera-dependent Updated (PreventCullingSystem.cs:103-186). A generic diff must ignore these.
- [V] Anarchy AnarchyPlopSystem post-processes Applied entities based on the local active tool and local Anarchy toggle. It adds PreventOverride/TransformRecord/Elevation, removes Overridden/Attached and rewrites the parent SubObject buffer (AnarchyPlopSystem.cs:222-344). Under intent replay the host would use its own tool context.
- [V] Anarchy ResetTransformSystem (ModificationEnd) overwrites Transform from TransformRecord on every Updated entity, on every machine (ResetTransformSystem.cs:60-160). Transform and TransformRecord must be replicated atomically. CheckTransformSystem only refreshes TransformRecord for the local MoveIt selection, which it reads via reflection (CheckTransformSystem.cs:157-188).
- [V] MoveIt makes all edits as direct ComponentLookup writes (QGeneric.cs:124-170, QEntity.cs:241-288). Its Temp creation path is commented out (Tool/Creation.cs). Its control-point entities use PrefabRef(Entity.Null)+CullingInfo, which matches the save query (ControlPointManager.cs:26-64).
- [V] BetterBulldozer deletes sub-elements directly and creates standalone record entities with OwnerRecord{Entity}+PrefabRef (SubElementBulldozerTool.cs:625-743). On every machine, RemoveRegeneratedSubelementPrefabsSystem and frame-counted DeleteInXFrames (ToolUpdate) delete regenerated children (HandleDeleteInXFramesSystem.cs:84-110). It can also delete vehicles, cims and animals by radius.
- [V] Tree Controller's brush writes Tree.m_State directly, swaps PrefabRef in place, adds/removes the Tree component and toggles Decoration (TreeControllerTool.cs:818-954). LumberAndPauseTreeGrowthSystem toggles Decoration/LumberResource enabled bits in the Rendering phase. Decoration enabled means growth paused, because TreeGrowthSystem processes only trees with Decoration disabled (TreeGrowthSystem.cs:271).
- [V] Water Features creates WaterSourceData entities without PrefabRef (CustomWaterToolSystem.cs:368-373, 1102-1154) and creates a dummy sea source (TidesAndWavesSystem.cs:195-238). Its sim systems read the locally computed GPU water surface, so they must run host-only. It changes global WaterSystem parameters, disables vanilla WaterDamageSystem/SubmergeSystem, and stores per-city settings in the save through IDefaultSerializable systems (ChangeWaterSystemValues.cs:21-185).
- [V] Plop the Growables disables vanilla ZoneCheckSystem (Mod.cs:74). Its PloppedBuildingSystem (ModificationEnd, every machine) tags any untagged zoned building as plopped, and as Historical if LockPloppedBuildings is on. A client that receives a building without its SpawnedBuilding tag would mis-tag it (PloppedBuildingSystem.cs:52-82).
- [V] Zoning Toolkit stores ZoningInfo on road edges. Its Modification4B system resizes Block.m_Size/ValidArea on every peer after vanilla BlockSystem regenerates blocks. For newly applied roads it uses the system's local UI zoningMode (ZoningToolkitModSystem.cs:356-475; BlockUtils.cs:54-111).
- [V] 529 Tiles (PostDeserialize) and Historical Start (Deserialize phase) mutate MapTile Native, milestone prefabs, unlock events and UnlockRequirement buffers based on the loading player's settings. The 529 Tiles upkeep patch changes city expenses (CityServiceBudgetSystem.cs:891).
- [V] Line Tool uses the vanilla CreationDefinition pipeline, but its random seeds re-roll every 2 seconds of Time.time (LineToolSystem.cs:900-903, 1004-1026). Intents must carry resolved points and seeds.
- [W] Traffic disables vanilla LaneSystem and replaces it with TrafficLaneSystem. It has its own Generate/Apply Temp pipeline, and its serializable buffers hold Entity references (ModifiedLaneConnections, GeneratedConnection, DataOwner). It must be installed at the same version on all peers.
- [U] Find It, Extended Tooltip, I18N Everywhere, Unified/Asset Icon Library, Skyve, Toggleable Overlays, Employment Tracker and Cim Census are classified local-only from their purpose. Road Speed Adjuster is probably world-changing, but I found no source to confirm it.

**Risks**

- Intent replay (Design B) cannot reproduce many mod actions. They are direct writes outside the Temp pipeline, depend on the local tool context, or use time-varying random seeds. Each would need a bespoke intent type and host executor.
- Per-machine enforcement and derivation systems will fight replicated state unless they are suppressed on clients. Examples: Anarchy ResetTransform/RemoveOverriden/PreventOverride/SetRetainingWall, Plop's PloppedBuilding/SelectiveZoneCheck, BetterBulldozer's RemoveRegenerated/AutoRemove/DeleteInXFrames, Tree Controller's Rendering-phase growth pause, Water Features sim systems, and Zoning Toolkit block resizing.
- Load-time mutators driven by local settings (529 Tiles, Historical Start, Plop ExistingBuildingSystem, Anarchy/BetterBulldozer OnGameLoadingComplete) can diverge a joiner's world right after it loads the host snapshot.
- Entity identity keyed on PrefabRef misses water sources and wrongly includes MoveIt control points. Mod components containing Entity fields (BetterBulldozer, Traffic) break without ID remapping.
- Enabled-bit and in-place PrefabRef or archetype changes (Tree Controller, Decoration, LumberResource) are invisible to a naive value diff.
- Non-atomic arrival of replicated components (for example Transform without TransformRecord, or a building without SpawnedBuilding, or an edge without ZoningInfo) triggers mod systems that snap back or mis-tag before ModificationEnd.
- Prefab-level mutations (unlock state, UnlockRequirement, MilestoneData, PlaceableObjectData cost, ToolErrorData, added prefabs) and global WaterSystem parameters are not entity state. They need separate session-settings or prefab channels and mod-version and settings parity.
- Water simulation runs on the GPU per machine. Water Features feedback loops amplify divergence even when sources and parameters match.
- Traffic replaces vanilla lane generation, and several other mods add prefabs or change validation. A peer with a missing or different-version mod will derive different lanes, blocks or validation results.

**Open questions**

- Road Speed Adjuster: which components and systems does it write? Answering this needs a decompile of its DLL, which is outside this pass's allowed paths.
- Traffic: do its data entities (DataOwner/ModifiedConnections) carry PrefabRef? Does ModificationDataSyncSystem (Modification4B) delete or reset data on edge updates in a way that would race on clients?
- What is the intra-phase ordering of mod systems registered with UpdateAt relative to vanilla systems in the same phase (for example Anarchy EnableToolErrorsSystem versus ValidationSystem, both at ModificationEnd)?
- Is a per-mod suppression registry acceptable, or should the layer attempt a generic client-side write guard on replicated components?
- Should mod settings that affect simulation be forced from host to clients (requires a per-mod ModSetting adapter), or should differing settings simply block joining?
- Can tool-local vanilla entities (for example CreationDefinition without Temp) match the save query between ToolUpdate and Modification1 and pollute a generic diff?

## 10-player-actions.md

41 files in Game.UI.InGame register 182 TriggerBindings. About 45 of them change shared city state, through eight different mutation mechanisms: event entities on EndFrameBarrier (Modify, Unlock, ColorUpdated), Deleted added via EndFrameBarrier, direct buffer or component writes with no tag, managed-system setters (TaxSystem, SimulationSystem.selectedSpeed, NameSystem, CityConfigurationSystem.cityName), a queued action (LoanSystem.ChangeLoan, applied in Modification1), and tool activation. There are a few clean choke points. PoliciesUISystem.ModifyPolicy (PoliciesUISystem.cs:237) is the only Modify producer and carries 11 UI actions (policies, out-of-service, emptying, ticket price, vehicle count, schedules, line state). NameSystem.SetCustomName handles all renames. The economy and progression go through public setters on TaxSystem, CityServiceBudgetSystem, ServiceFeeSystem, LoanSystem, DevTreeSystem and MapTilePurchaseSystem. Report 04's open question is resolved: District, Building and Route modifiers are recomputed from Policy only by Policies.ModifiedSystem (Modification4, on Modify events) and by the ModifierInitialize systems (on Created entities). CityModifier is also recomputed every 256 simulation frames by CityModifierUpdateSystem, which folds in effect-provider buildings weighted by efficiency. So replicate policy changes as Modify events, not as direct buffer writes. On the host, replayed UI commands must run in UIUpdate or after AllowBarrier<EndFrameBarrier>, because SafeCommandBufferSystem throws at MainLoop start. For client tool applies, the recommended design is: capture the Temp set in a system ordered first in the ApplyTool phase (which runs only on apply frames), let the vanilla apply run locally as a prediction, then capture the exact result set (entities tagged Applied/Created/Updated plus deleted originals) before Modification1. The host validates and commits that change-set with the direct-write path, never touching its own Temps, and the originating client binds or rolls back its predicted entities. An optional no-predict gate rewrites applyMode from Apply to Clear just before ToolOutputSystem.


**Key findings**

- Count [V]: 41 files in Game.UI.InGame register 182 TriggerBindings; CinematicCameraUISystem also has CallBindings. All are catalogued with file:line and a sync class: SHARED, PER-PLAYER, LOCAL or tool state.
- Policy choke point: 11 UI actions funnel into PoliciesUISystem.ModifyPolicy (PoliciesUISystem.cs:237-242), which creates an Event+Modify entity on EndFrameBarrier. Game.Policies.ModifiedSystem consumes it in Modification4 (SystemOrder.cs:146), rebuilds options and modifiers in RefreshEffects (ModifiedSystem.cs:250-299), and enqueues PolicyActivated and FreePublicTransport triggers.
- Modifier recompute verified: District/Building/Route modifiers change only on a Modify event (ModifiedSystem) or on Created entities (the ModifierInitialize systems, Modification4). CityModifier is also recomputed every 256 frames by CityModifierUpdateSystem (CityModifierUpdateSystem.cs:269-271), which includes CityEffectProvider buildings weighted by efficiency.
- DefaultPoliciesSystem (Modification3) appends prefab default policies to every Created entity that has a Policy buffer (DefaultPoliciesSystem.cs:31-58). Remote creation with a pre-filled Policy buffer would therefore duplicate the defaults.
- Economy actions are direct managed or buffer writes. TaxSystem keeps a 92-int NativeArray (TaxSystem.cs:193). CityServiceBudgetSystem.SetServiceBudget writes a singleton buffer and adds Updated via EndFrameBarrier (CityServiceBudgetSystem.cs:1084-1119). ServiceFeeSystem.SetFee writes the City buffer with no tag (ServiceFeeSystem.cs:508-520). LoanSystem.ChangeLoan queues an action applied in Modification1 that changes PlayerMoney (LoanSystem.cs:33-47,130-137).
- DevTreeSystem.Purchase writes the DevTreePoints singleton directly and emits an Unlock event, which UnlockSystem processes in MainLoop. MapTilePurchaseSystem.PurchaseSelection subtracts money directly and removes Native plus adds Updated via EntityManager. It depends on the selection tool being active (MapTilePurchaseSystem.cs:92-114,355-367), so the host must reimplement the purchase instead of calling it.
- Untagged direct writes that change simulation: VisualCustomizeSection.toggleHistorical flips Building.m_Flags, and Historical blocks level-up and abandonment in BuildingUpkeepSystem.cs:239-282. SelectVehiclesSection edits the VehicleModel buffer, and DistrictsSection.removeDistrict edits the ServiceDistrict buffer.
- SelectionToolSystem in service-district mode never applies. It writes the owner's ServiceDistrict buffer directly from a job and adds Updated (SelectionToolSystem.cs:390-423, 813-947), so this tool mutation bypasses Apply.
- TimeUISystem forces simulation speed to 0 when the window loses focus or a UI pause barrier is observed (TimeUISystem.cs:115-137). Photo mode can set speed 0-8 (PhotoModeRenderSystem.cs:765-780). pausedAfterLoading sets speed on load (SimulationSystem.cs:213).
- Host timing: EndFrameBarrier is a SafeCommandBufferSystem whose CreateCommandBuffer throws between its playback and AllowBarrier<EndFrameBarrier> (Game/SafeCommandBufferSystem.cs:15-22; SystemOrder.cs:49,62). Replayed UI commands must run in UIUpdate or after that barrier.
- Apply frame anatomy: ToolSystem.applyMode returns m_LastTool.applyMode (ToolSystem.cs:147-157), and ToolBaseSystem.applyMode has a protected setter (:182). ToolOutputSystem dispatches to ClearTool or ApplyTool (ToolOutputSystem.cs:22-30). New preview definitions are queued in ToolOutputBarrier, which plays back after ApplyTool, so at ApplyTool start the Temps and their definitions are exactly the validated previous-frame preview.

IP2 = UpdateBefore in the ApplyTool phase, the capture point for Temps and definitions. IP3 = UpdateBefore Modification1, where entities tagged Applied are exactly the primary Apply* outputs, because derived systems add Applied only later in Modification. TempFlags.Cancel is not honoured by the zone, area or route apply systems, so it cannot serve as a universal suppressor.

- UpgradeDeletedSystem (ToolUpdate) reacts to any ServiceUpgrade+Deleted and regenerates the owner's sub-nets and sub-areas as Permanent definitions with time-seeded seeds (UpgradeDeletedSystem.cs:134,245-253,343-349). Clients must not run it for replicated deletions.
- Per-tool state is catalogued with verified names and modes for the Net, Object, Zone, Area, Route, Bulldoze, Terrain, Upgrade, Water and Selection tools. Zone mode and overwrite are baked into Zoning.m_Flags, and NetTool draws a fresh time-seeded RandomSeed on each apply. Under the change-set design the host needs none of this state.

**Risks**

- Under the predict-and-ship design the host commits geometry computed by the client. Validation (revision checks, cost, unlock state, area ownership) is only partial; a full server-side re-validation would need running Generate and ValidationSystem, which conflict with the host player's Temps.
- A direct commit skips Apply-only bookkeeping: Recent, TriggerAction(ObjectCreated), money and Applied semantics. The host must reproduce each of these explicitly or chirps, tutorials, refunds and stats diverge.

Contradiction (a): resolved with a hybrid. ## 13-derived-identity-regeneration.md

Some derived entities can be regenerated identically on every peer, but only some families keep the same identity, which the replication design needs.

Lanes: LaneSystem reuses lane entities by LaneKey (three PathNodes, lane prefab entity, Master/Slave flags). Edge lanes, edge-connection lanes and building sub-lanes get keys from prefab and composition data only, so they are deterministic. Intersection (node) lanes are not: their middle PathNode is a running counter, the generation order is partly sorted by Entity.Index, and two-way lane direction is picked by comparing owner entity indices. Lane identity therefore needs a portable key (owner NetId plus PathNodes re-encoded with NetIds) with a geometric fallback. Better still, keep lane references off the wire wherever possible.

Sub-objects use the owner's PseudoRandomSeed, but which placeholder sub-objects appear depends on simulation state (renters, brands, citizen ages, household wealth, pets, snow). Tree sub-objects also carry simulated growth.

Zone blocks are reused on exact Block equality. Vanilla carries painted zoning over only from blocks deleted in the same frame, inside CellCheckSystem. Host zoning must then be applied as an m_Zone overlay, with the block tagged Updated, one frame after the edit.

Building sub-nets, sub-areas and area-spawned objects are never regenerated. Their Permanent definitions are seeded per machine by RandomSeed.Next(). Replaying them also depends on terrain and water height, the per-machine BuildOrder counter and exact-transform owner matching. Verdict: do not forward definitions from host to clients. Replicate the resulting state as first-class entities with host NetIds. Definitions stay a client-to-host intent format only. This resolves the contradiction in favour of report 02 §10.

Aggregates keep their identity across splits but not deterministically across merges. Custom names are keyed by Entity. RandomLocalizationIndex, RouteNumber and VehicleModel are set by local initializers and must be overwritten with host values after those run. Districts and Building.m_RoadEdge are recomputed on every peer. NetCompositionData needs no identity.


**Key findings**

DistrictModifier is a pure function of the Policy buffer (DistrictModifierInitializeSystem.cs:82-128, 181). Building.m_RoadEdge is recomputed by RoadConnectionSystem in Modification4B, which also maintains ConnectedBuilding (RoadConnectionSystem.cs:591-647, 2188-2218).
- NetCompositionData is a per-prefab cache keyed by (prefab, CompositionFlags) (CompositionSelectSystem.cs:1228-1277) and needs no identity.

**Risks**

- The Traffic mod replaces vanilla LaneSystem with TrafficLaneSystem (report 09, web source). No local source is available, so the LaneKey and PathNode analysis must be re-verified with it installed.
- Node lanes, node secondary objects and aggregate tie-breaks depend on Entity.Index ordering and on ConnectedEdge buffer order. These cannot be made peer-stable by replicating source data alone; it would need a patch that sorts ConnectedEdge, or geometric-fallback matching.
- Burst float code generation may differ between CPUs (report 03, N11), so float-based keys (Block positions, lane curve endpoints) must be quantized.
- Vanilla zoning carry-over works only if the old edge is deleted and the new edges are created in the same frame on the client. A split change-set breaks this.
- Initializer systems overwrite replicated fields on Created entities: RandomLocalizationInitializeSystem, Routes.InitializeSystem and DistrictModifierInitializeSystem. Host values must be patched in after they run.
- Client-local UpgradeDeletedSystem, WetnessSystem snow events and SubElementDeleteSystem can create structural divergence or duplicates unless disabled or reconciled.
- Sub-object regeneration depends on simulation state (renters, households, snow). Clients that do not simulate must apply that state and synthesize RentersUpdated or Updated, otherwise their sub-object sets go stale.
- Custom names are keyed by Entity and are lost when an aggregate is deleted in a merge. They need a NetId-keyed table re-applied after reconciliation.
- When an aggregate merge deletes an entity, choosing which aggregate survives on the client needs a reconciliation system running after AggregateSystem in the same frame, before PrepareCleanUpSystem destroys entities.

**Open questions**

- Does NameSystem.OnUpdate ever run? It is not registered in SystemOrder and nothing calls it; this needs a runtime check.
- Does the Traffic mod's TrafficLaneSystem keep vanilla LaneKey and PathNode semantics, and which of its components store Entity references to lanes?
- Is a client-side patch that sorts ConnectedEdge by (BuildOrder, NetId) after ReferencesSystem feasible and safe? It would make node lanes, node secondary objects and aggregate tie-breaks deterministic.
- Does the reuse branch of SecondaryObjectSystem reset tree age on every regeneration (around SecondaryObjectSystem.cs:3499-3504)? This affects whether secondary-tree growth must be re-sent after each owner update.
- Does RoadConnectionSystem's creation of utility connection lanes and objects use any randomness? It was not fully traced (RoadConnectionSystem.cs:834-1938).
- Do LocalizationCount values differ between game languages in practice? If so, RandomLocalizationSystem re-rolls replicated indices on clients with a different locale.

## 14-progression-feedback.md

Progression in CS2 is driven by one-frame event entities (Event+Unlock, Event+MilestoneReachedEvent). The same producers that create them also apply the rewards: MilestoneSystem writes PlayerMoney and Creditworthiness directly, and DevTreeSystem adds points for every MilestoneReachedEvent it sees. The safe co-op pattern is therefore: disable every reward producer on clients, replicate the resulting state (XP, MilestoneLevel, DevTreePoints, money, prefab Locked bits), and have a client apply system synthesize the matching event entities before ModificationSystem, so the vanilla UI refreshes. UI systems detect unlocks only through Unlock entities (PrefabUtils.HasUnlockedPrefab), so writing an enable bit directly leaves the toolbar and asset menu stale. Clients should apply unlocks by creating Event+Unlock(prefab) and let vanilla UnlockSystem.ProcessEvents flip the bit. The unlock set is already carried by the save (ResolvePrefabsSystem). UnlockRequirementData.m_Progress is not saved and must be sent after the join. Icons cannot be regenerated on clients: about 30 simulation systems add them on edge-triggered thresholds with private flags. Clients should keep IconCommandSystem running and feed it replicated add/remove commands through CreateCommandBuffer, and keep Marker icons (they depend on the local infoview) per player. Chirps, text variants, likes and life-path events use wall-clock RNG and must be host-generated and replicated; RandomLocalizationInitializeSystem would re-roll replicated chirp text on clients. Tutorials are stored in user settings, but they create Unlock events (including UI groups), unlock map tiles when unlockMapTiles is set, and the host's unfinished intro tutorial blocks milestones for the whole city. Achievements are already disabled for every peer: any loaded code mod adds an entry to usedMods, which AchievementTriggerSystem ANDs into achievementsEnabled, and usedMods is saved, so co-op saves stay marked as modded.


**Key findings**

- [V] MilestoneSystem (ModificationEnd) returns early if TutorialSystem.tutorialIntroUnfinished. It raises at most one milestone per frame, writes PlayerMoney.Add(reward) and Creditworthiness += loanLimit directly with EntityManager, and creates Event+MilestoneReachedEvent and Event+Unlock through ModificationEndBarrier (MilestoneSystem.cs:70-116).
- [V] DevTreeSystem adds dev points for every MilestoneReachedEvent entity (DevTreeSystem.cs:31-56, 128-146). DevTreeSystem.Purchase subtracts points immediately and queues Unlock(node) on EndFrameBarrier (:157-175). Purchased nodes are DevTreeNodePrefab entities with Locked disabled, and node effects come only through other prefabs that list the node in their UnlockRequirement.
- [V] XPBuiltSystem grants XP for every Created, non-Temp entity with PrefabRef and adds PlacedSignatureBuildingData to the signature prefab (XPBuiltSystem.cs:45-83). On a client, replicated buildings would therefore earn XP again unless this system is disabled.
- [V] MilestoneUISystem's achievedMilestoneXP and nextMilestoneXP read fields that are computed only in MilestoneSystem.OnUpdate (MilestoneUISystem.cs:388-396), so they show 0 if MilestoneSystem is simply disabled on clients. The milestone list refreshes only when a MilestoneReachedEvent exists (:316-324). XP toasts come from XPSystem.TransferMessages, and the public AddMessage method can be fed by a mod (:330, 359-372).
- [V] Map-tile permits are not stored anywhere. They are computed as 9 plus the sum of m_MapTiles over milestone prefabs with Locked disabled, minus owned tiles (MapTilePurchaseSystem.cs:163, 255-273).
- [V] The prefab Locked bit is saved per prefab (BeginPrefabSerializationSystem.cs:75-97; ResolvePrefabsSystem.cs:122-150) and read by gameplay systems (CrimeAccumulationSystem.cs:290; PropertyUtils.cs:629-641). UnlockRequirementData.m_Progress is not saved: it is reset on load (ResetUnlockRequirementSystem) and recomputed by the requirement systems.
- [V] Every UI consumer (toolbar, asset menu, dev tree, policies, infoviews, statistics, signature popup, UIHighlight 'new' markers) refreshes only when an Unlock event entity exists (ToolbarUISystem.cs:151, 216-227; PrefabUtils.cs:16-37). UnlockSystem (MainLoop, after ModificationSystem) processes those events idempotently and then repeats the requirement check until nothing new unlocks (UnlockSystem.cs:143-224).
- [V] UnlockAllSystem runs on clients when unlockAll is set (CityConfigurationSystem.cs:195-198) and calls MilestoneSystem.UnlockAllMilestones, which adds rewards to money and creditworthiness (MilestoneSystem.cs:144-170).
- [V] IconCommandBuffer has 42 producer files: 31 in GameSimulation (edge-triggered, e.g. GarbageAccumulationSystem.cs:216-223), plus Modification-phase and tool producers. IconCommandSystem's Add is idempotent per owner, prefab and target (IconCommandSystem.cs:186-338). Its queues are disposed only in OnUpdate or OnStopRunning, so disabling the system leaks them. Marker icons depend on the local infoview (MarkerCreateSystem.cs:415-489).
- [V] Chirp creation uses RandomSeed.Next() for the variant, sender, likes and virality (CreateChirpSystem.cs:141-183, 509). RandomLocalizationInitializeSystem re-rolls the text index of every Created entity (RandomLocalizationInitializeSystem.cs:49-50, 123). ChirpFlags.Liked is written only by ChirperUISystem's addLike/removeLike triggers and is cosmetic (ChirperUISystem.cs:141-157, 237). The traffic-accident trigger value depends on the local Camera.main (TriggerSystem.cs:140-143, 483-487).
- [V] TriggerSystem.CreateActionBuffer asserts that the system is Enabled. Non-simulation producers that run on clients include Events.InitializeSystem, AddHealthProblemSystem, Policies.ModifiedSystem, CitizenInitializeSystem, RemovedSystem, NotificationTriggerSystem and ApplyNet/ApplyObjects. TriggerSystem also routes game events to TutorialEventActivationSystem (TriggerSystem.cs:253-264, 405-411).
- [V] Tutorial state lives in SharedSettings.userState.shownTutorials (UserState.cs:9-14). Tutorial runtime tags are not serialized, but tutorial prefabs' Locked bits are. ManualUnlock creates Unlock events for UI groups through ForceUIGroupUnlockData (TutorialSystem.cs:973-991). When unlockMapTiles is set, TutorialSystem calls MapTilePurchaseSystem.UnlockMapTiles(), depending on the local player's tutorial settings (:308-317, 897-906, 1051-1062). Tutorials have no C# speed or tool-blocking code.
- [V] EventJournalInitializeSystem (Mod4) creates a journal entry for every Created event with JournalEvent, so replicated events would produce duplicate entries. EventJournalUISystem reads the managed EventJournalSystem.eventJournal list and its callbacks (EventJournalUISystem.cs:38-80).
- [V] Achievements: MenuUISystem sets achievementsEnabled before a load (MenuUISystem.cs:731, 770, 804). AchievementTriggerSystem.OnGameLoaded ANDs it with usedMods.Count == 0 (:427-430). usedMods holds every loaded code mod (CityConfigurationSystem.cs:255-263; ModManager.cs:222-228) and is loaded from and saved to the city (:326-337, 412-421).
- [V] GameModeSystem runs only in the Deserialize phase (SystemOrder.cs:797) and applies the mode prefab, which rewrites MilestoneData, UnlockRequirement and XP parameters (MilestonesMode.cs:42-62; UnlockAtStartMode.cs:25-46). Clients can apply it themselves from the snapshot. BudgetUISystem shows the 'Government' line only if GameModeGovernmentSubsidiesSystem.Enabled is true (BudgetUISystem.cs:54; GameModeGovernmentSubsidiesSystem.cs:35-38).
- [V] RichPresenceUpdateSystem reads Population, CitySystem.moneyAmount, MilestoneLevel and cityName. CitySystem (Modification1) caches money and XP every frame and must keep running on clients (CitySystem.cs:45-52). Photo mode writes selectedSpeed (PhotoModeRenderSystem.cs:765-780). The radio reads RadioTagSystem events and brand popularity (Radio.cs:1543-1561, 1683-1742).

**Risks**

- Replicating both progression events and state applies rewards twice (money, creditworthiness, dev points, XP). Clients must disable XPBuiltSystem, NetXPSystem, XPSystem, XPAccumulationSystem, DevTreeSystem, UnlockAllSystem and the requirement systems, and shim MilestoneSystem.
- Requirement buffers can differ per machine, because mods such as HistoricalStart and the game-mode prefabs rewrite UnlockRequirement locally. A client running UnlockSystem's requirement loop or the requirement systems could unlock prefabs the host never unlocked.
- Vanilla has no way to relock a prefab with a UI refresh. An Unlock event for a relocked prefab unlocks it again, so relock or desync repair needs an unverified workaround.
- Icons cannot be regenerated locally. Filtering vanilla icon commands on clients without losing legitimate local ones (Temp previews, Marker icons, tool feedback) needs careful classification. Marker icons from the host's infoview may arrive in the join snapshot.
- RandomLocalizationInitializeSystem re-rolls text variants of every replicated Created entity (chirps and probably names), causing visible text divergence unless it is patched.
- Disabling TriggerSystem breaks game-event-driven tutorials on clients and trips the CreateActionBuffer assert and a TempJob queue leak. Keeping it requires muting chirp, life-path and radio outputs.
- Tutorials mutate shared state (map tiles, the Map Tiles feature, UI-group unlocks) from per-player settings, and the host's unfinished intro tutorial blocks milestones for all players.
- Some systems' Enabled flag is read by the UI (GameModeGovernmentSubsidiesSystem through BudgetUISystem). Disabling host-only systems via Enabled therefore changes client UI.
- Any co-op save permanently disables achievements because usedMods is persisted. This is user-visible but cannot be avoided without patching the platform gate.
- The traffic-accident chirp condition depends on the host's local camera position, a small quirk that cannot be matched for clients.

**Open questions**

- Do the milestone popup, signature popup, advisor and tutorial panels pause the simulation through the JS time.simulationPausedBarrier? This needs checking with -uiDeveloperMode.
- Confirm at runtime that ComponentType.Exclude<Locked>() matches prefabs with Locked disabled (Entities 1.x semantics assumed by MapTilePurchaseSystem.cs:163).
- Does the proposed relock UI refresh (an Unlock event targeting an already-unlocked prefab with UIObjectData) work without side effects?
- Does MarkerCreateSystem.PostDeserialize remove the host's infoview markers for a joining client?
- Is the Temp/Marker/Transaction filter enough to separate local icon commands from simulation ones, e.g. ConnectionWarningSystem for applied objects?
- Which layer owns the RandomLocalizationIndex re-roll fix for all replicated Created entities: entity replication (report 04) or this subsystem?
- Should followed citizens and life paths be shared (host-authoritative, max 50) or per player (needs host-side union generation)?
- Should clients force a refresh of the prefabDetails binding after progress deltas? Vanilla refreshes it only on order-version changes or unlocks.
- Does GameModeGovernmentSubsidiesSystem's double registration (ModificationEnd and GameSimulation) honor the 8192-tick interval in the ModificationEnd slot?

## 15-moving-objects-agents.md

Each moving entity is drawn from four inputs: its UpdateFrame (phase u), its 4-slot TransformFrame ring, RenderingSystem.frameIndex and RenderingSystem.frameTime (ObjectInterpolateSystem.cs:4332-4360, 3041-3042). It always shows the host state at render tick R-32. The two slots it blends hold the frames written at host ticks F1 and F1+16, where F1 ≡ u (mod 16). If the client's UpdateFrame differs from the host's, each entity is shifted in time by up to 15 ticks (several metres at road speed). The vanilla ring also only accepts a frame for tick T while the reader's render tick is within [T-16, T+16): 32 ticks, which is ±67 ms at speed 4. The host stays inside it because RenderingSystem keeps the render tick within ±15 ticks of the simulation tick (RenderingSystem.cs:175-221). Clients therefore need three things: a staging ring with a just-in-time writer in PreCulling, a clock running D ticks behind the host, and extrapolation when a frame is missing. Spawning works from the prefab archetypes (MovingObjectPrefab, TrainPrefab), with the host's UpdateFrame plus the Applied tag so that UpdateGroupSystem keeps the phase. The vanilla reference systems then rebuild OwnedVehicle, CarKeeper, Passenger, CurrentTransport, LaneObject and RouteVehicle links from Created/Deleted. Movers must never be tagged Updated on clients: UpdateGroupSystem resets their frames and the vehicle and creature initializers re-run with random values. Light, siren and boarding effects refresh only when EffectsUpdated is added. Several Modification-phase systems spawn or mutate agents and must be disabled on clients: ParkedVehiclesSystem, ObjectEmergeSystem, GroupSystem, FixParkingLocationSystem, FixLaneObjectsSystem and ParkingLaneDataSystem. The moving search tree only holds objects that are not on a lane, so the host should select interest by scanning, per tick, only the 1/16 of entities whose frame was just written. Info panels refresh every 256 ticks, so on-demand inspection can stream the selected entity and its related entities at that rate, aligned across peers. Estimated bandwidth with ~3k objects in interest and ~11 B quantized frames: ~125/250/500 KB/s at speeds 1/2/4; full replication of ~21k objects is 0.9-3.5 MB/s, which is not feasible.


**Key findings**

- CalculateUpdateFrames uses RenderingSystem.frameIndex/frameTime and the UpdateFrame shared component (copied into PreCullingData.m_UpdateFrame, PreCullingSystem.cs:660/927-932). It blends slots (n>>4)&3 and +1 with n = R-u-32, which always shows the state at tick R-32 [V].
- Movers write slot (frameIndex>>4)&3 for entities with UpdateFrame == frameIndex&15. A frame's position is the midpoint of the 16-tick step, and its flags hold the light, signal and brake bits (CarMoveSystem.cs:181-182, 207-261, 420-423) [V].
- A frame for tick T may only be written while the reader's render tick is in [T-16, T+16). Earlier overwrites the frame on screen; later is too late. The host fits because render offset is clamped to ±15 ticks (RenderingSystem.cs:175-221) [V]. Clients need a staging buffer plus a just-in-time slot writer in PreCulling before PreCullingSystem [I].
- A client UpdateFrame that differs from the host's shifts each entity by up to 15 ticks; the host value must be replicated. UpdateGroupSystem keeps an existing UpdateFrame only if the entity has Applied (UpdateGroupSystem.cs:408-446); Applied is removed by CleanUpSystem.cs:24-28 [V].
- Any Updated + InterpolatedTransform entity gets all 4 frames reset to its static Transform (UpdateGroupSystem.cs:561-615). Game.Vehicles.InitializeSystem re-runs on every Updated vehicle, resets CarNavigation, randomizes lane offset via RandomSeed.Next and repositions unspawned vehicles (InitializeSystem.cs:1330, 341-350, 606-739) [V].
- PreCulling first tests Transform with a ~278 m slack before looking at frames (PreCullingSystem.cs:1152-1171), so clients must keep Transform current. Moving.m_Velocity drives audio and Driving clips (AudioManager.cs:1370-1372; ObjectInterpolateSystem.cs:540-558) [V].
- EffectControlSystem re-evaluates effects only for Updated/Deleted/EffectsUpdated/BatchesUpdated entities (EffectControlSystem.cs:1087-1098). Siren, boarding and light conditions read Car.m_Flags, role m_State and the frame flags (EffectControlData.cs:274-560). Movers and AIs add EffectsUpdated on change (CarMoveSystem.cs:265-279, PoliceCarAISystem.cs:904-985) [V].
- HumanMoveSystem emits SubObjectsUpdated events and BatchesUpdated when the activity changes (props). Human animation reads frame m_State, m_Activity and m_StateTimer, the Human flags and the CurrentVehicle prop (HumanMoveSystem.cs:406-424; ObjectInterpolateSystem.cs:4135-4252) [V].
- TransformFrame saves only state, activity and timer. Positions are rebuilt on load by TransformFrameSystem from Transform/Moving (TransformFrame.cs:57-75; TransformFrameSystem.cs:49-131); TrainBogieFrame is reset from TrainCurrentLane (TrainBogieFrameSystem.cs:27-44) [V].
- Moving and stopped archetypes are ObjectData.m_Archetype and MovingObjectData.m_StoppedArchetype. TransformFrame, InterpolatedTransform and navigation components exist only when Moving is present (MovingObjectPrefab.cs:20-59; TrainPrefab.cs:63-130). Parked<->moving swaps are fixed remove/add type sets that include Updated (PersonalCarAISystem.cs:1128-1142; ImpactSystem.cs:472-529). RequiredComponentSystem is load-time migration only [V].
- Vehicles.ReferencesSystem and Creatures.ReferencesSystem rebuild links on Created/Deleted: OwnedVehicle, CarKeeper.m_Car, BicycleOwner, GuestVehicle, Passenger, CurrentTransport, OwnedCreature, RouteVehicle, LaneObject or moving tree (Vehicles/ReferencesSystem.cs:282-477; Creatures/ReferencesSystem.cs:80-154). CarKeeper is enableable and its enabled bit is gameplay state [V].
- These Modification-phase systems would spawn or mutate on clients: ParkedVehiclesSystem (Created service buildings without Applied), ObjectEmergeSystem, GroupSystem, FixParkingLocationSystem, FixLaneObjectsSystem, ParkingLaneDataSystem; also a TransportDepot maintenance write in Vehicles.ReferencesSystem (l.494-523) [V].
- Raycast selection of moving objects uses the moving search tree plus lane LaneObject buffers (RaycastSystem.cs:948-1023). The moving tree only holds objects not on a lane with a LaneObject buffer (LaneObjectSystem.cs:93-104), so it is unsuitable for host area selection alone [V].
- Camera API: CameraUpdateSystem.activeViewer/position/direction/zoom/activeCameraController (CameraUpdateSystem.cs:134-216), Viewer.frustumPlanes/bounds (Viewer.cs:44-58), CameraController.pivot/zoom, OrbitCameraController.followedEntity [V].
- SelectedInfoUISystem refreshes sections every 256 ticks via UIUpdateState, or on Updated/BatchesUpdated, and RequestUpdate forces a refresh (SelectedInfoUISystem.cs:181, 343-346, 383). Selection position and follow camera re-interpolate from frames + UpdateFrame (l.578-670; OrbitCameraController.cs:286-289) [V].
- CitizenUIUtils.GetStateKey uses GetComponentData on the household (l.238-239) and throws if related entities are missing. DispatchedVehiclesSection scans all vehicles with ServiceDispatch (l.263); LineVisualizerSection needs PathOwner/PathElement/current lane/TransformFrame of route vehicles (l.816-1016) [V].
- Bandwidth estimates [I]: ~21k movers × 3.75 Hz × speed. Raw 52-104 B/update gives 4-33 MB/s; quantized delta ~11 B gives 0.87/1.7/3.5 MB/s for everything, ~124/248/495 KB/s for a 3k interest set, and ~83/165/330 KB/s with half-rate far field. Global spawn/despawn stream ~8-20 KB/s at speed 1.

**Risks**

- The 32-tick write window of the 4-slot ring cannot be met reliably by network delivery, especially at speed 4 (±67 ms). Without staging and extrapolation there will be jumps and 64-tick backward snaps.
- UpdateFrame divergence between host and client gives per-entity time offsets of up to 15 ticks (several metres) and inconsistent follow and selection positions.
- A generic receiver that adds Updated to movers resets their frames and re-runs initializers with machine-local randomness (RandomSeed.Next), freezing or jittering traffic.
- Vanilla Modification systems (ParkedVehiclesSystem, ObjectEmergeSystem, GroupSystem, FixParkingLocationSystem, FixLaneObjectsSystem, ParkingLaneDataSystem, TransportDepot write in Vehicles.ReferencesSystem) create duplicate agents or mutate host-owned state on clients unless gated.
- Effects (sirens, headlights, boarding) go stale unless the client adds EffectsUpdated whenever replicated flags or states change.
- Vehicles cannot be clicked on clients unless LaneObject buffers or moving-search-tree entries are maintained for replicated movers.
- UI exceptions (e.g. CitizenUIUtils.GetStateKey) if the related entities of a selected entity are not present on the client.
- Burst-inlined CalculateUpdateFrames/CalculateTransform cannot be patched reliably, so the 32-tick lag and slot math are fixed; all adaptation must be done in data.
- Host bandwidth at speed 4 with several clients (~0.3-0.5 MB/s per client) may exceed home upload. Needs per-client budgets, priority and reduced far-field rate.
- Lane identity remapping errors for CarCurrentLane/ParkedCar/TrainBogieFrame can hit unguarded Burst indexers (Vehicles.ReferencesSystem InitializeCurrentLaneJob l.68-69).
- Far-field staleness after camera teleports; the client clock lag D delays all client views (including tool feedback) by ~0.1-0.2 s.
- Possibly unbounded vanilla queue m_ResourceNeedingUpdateQueue in Vehicles.ReferencesSystem: enqueued but no dequeue was found in the file.

**Open questions**

- What are the real counts in a 100k city: moving vehicles, moving creatures, parked cars, interest-set sizes per zoom level, and lifecycle events per second? This needs an in-game diagnostic build.
- What is the effective NearCamera distance per vehicle size and LOD setting? It is needed to tune the interest radius.
- Can Game.Tools.Hidden + BatchesUpdated serve as a purely cosmetic hide for out-of-interest movers without side effects on UI and culling?
- Could section JSON be rendered on the host and its Entity references remapped (IJsonWriter Entity path, NameSystem.BindName), as an alternative to component-closure fetching?
- What should the replication policy be for ServiceDispatch buffers and service-request entities, which DispatchedVehiclesSection and the vehicle state keys need?
- Can TrafficRoutesSystem be fed on demand with path buffers only for matching vehicles, using host-side matching identical to its job?
- What is the jitter distribution of Steam P2P and relay links, to size the clock lag D and the staging ring depth?
- Should clients maintain LaneObject buffers (needed for road and bike infoviews and exact raycast) or rely only on the moving search tree?
